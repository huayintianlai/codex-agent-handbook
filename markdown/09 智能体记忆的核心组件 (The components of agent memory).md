# 09 智能体记忆的核心组件

The components of agent memory

>   **原文标题：**The components of agent memory **发布日期：**2026-11-06 **作者：**Lance Martin **预计阅读：**约 18 分钟  [查看官方英文原文 ↗](https://www.anthropic.com/research/components-of-agent-memory)

 索伦·克尔凯郭尔（Søren Kierkegaard）曾写道：生命只能*向后*理解，但必须*向前*生活。在为 AI 智能体设计记忆系统时，我们遇到了极为相似的困境。

 作为人类，我们在日常生活中时刻都在编码记忆。[海马体（hippocampus）](https://stanford.edu/~jlmcc/papers/McCMcNaughtonOReilly95.pdf)在其中扮演着核心角色：它能在当下迅速捕获经历，让记忆快速形成并立即可用。然而，最终只有[一部分经历](https://www.science.org/doi/10.1126/science.adk8261?referrer=https%3A%2F%2Fwww.google.com%2F)会被巩固为长期知识。

 这种巩固过程大多发生在大脑“离线”之时。当我们入睡或处于安静的[静息状态](https://www.nature.com/articles/s41467-018-06213-1)时，海马体会重放我们近期的经历。学界普遍认为，正是这一机制将这些零散经历逐步[提炼并整合](https://www.nature.com/articles/s41593-019-0467-3)进大脑的新皮层（neocortex）——即大脑中存储绝大多数我们称之为“知识”的区域。

 智能体记忆同样可以采用这种分工模式。智能体会将大量工作过程留存在日志或原始对话记录（transcripts）中。Letta 与加州大学伯克利分校（UC Berkeley）的研究人员曾提出**[休眠期计算（sleep-time compute）](https://arxiv.org/abs/2504.13171)**的概念，让模型利用交互间隙的空闲时间来重新组织既有上下文。同样的思路也可以帮助智能体梳理记忆：通过回溯反思执行日志来修正错误，或生成全新的笔记与结构化表示。这一过程通常[被称为](https://platform.claude.com/docs/en/managed-agents/dreams)**[“做梦”离线巩固（Dreaming）](https://research.google/blog/the-sleep-framework-a-new-way-for-llms-to-retain-knowledge-in-continual-learning/)**。

 我们发现，“做梦”离线巩固已成为赋予 Claude 高效记忆的得力工具。在本文中，我们将分享团队对智能体记忆的思考框架，并逐步剖析我们用于探索智能体记忆（涵盖“做梦”机制）的多项评估实验，阐明各个组件在记忆组织中所贡献的价值。

> **【图表说明】** 官方原图（中文化）：Claude 可通过“做梦”离线巩固（Dreaming）系统整理记忆——修正错误、创建笔记、构建新的记忆表示，或塑造预先加载进未来会话的注入上下文。



## 一、记忆笔记与记忆层级（Memory notes）

 我们所说的**“智能体记忆（agent memory）”**，是指 Claude 从过往经验（包括与用户的交互和分配给它的任务）中获取的知识，并在不同会话之间持久化留存，保存为日后可读取的上下文。这一定义排除了模型获取知识或管理上下文的其他方式，包括：模型**权重（weights）**的更新（即训练期间设定的内部参数变化）、**[上下文内学习（in-context learning）](https://www.anthropic.com/research/in-context-learning-and-induction-heads)**（单次对话窗口内部获得的知识），以及**[上下文压缩（compaction）](https://platform.claude.com/docs/en/build-with-claude/compaction)**（由 Claude 撰写、用来替代较早对话轮次的摘要，以便在新的上下文窗口中接着开展工作）。

 在人脑中，某段经历发生前、发生时或发生后释放的化学信号，能够将这段记忆[标记为重要](https://www.nature.com/articles/385533a0)。被标记的记忆在离线阶段往往会比未标记的记忆更频繁地被重放。这一称为**重放（replay）**的过程，有助于稳定这些记忆并将其整合进长期记忆之中。

 类似地，Claude 既可以在会话日志中实时标记具有显著性（salient）的事件以便日后检索，也可以直接将它们[写入](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)记忆存储（例如一个存放记忆笔记的文件夹）。但随之而来的核心问题是：**在尚不知晓接下来会发生什么的情况下，Claude 如何在当下判断哪些信息具有显著性（留存价值）？**

> **【图表说明】** 官方原图（中文化）：会话过程中，Claude 可将高显著性观察直接写入记忆笔记层。



## 二、记忆即预测：面向未来需求的自学习闭环（Memory can be a prediction）

 记忆有时就是一种**预测**。当智能体写下一条规则时，它实际上是在预测：自己所描述的规律未来还会再次派上用场。同理，写下一条经核实的事实，意味着预测未来会话中的智能体希望直接信赖该事实，而不必再次耗费成本去二次查验。随着模型代际演进，Claude 做出这类预测的能力已经有了大幅飞跃。

 不妨看看 **[Continual Learning Bench（CL-Bench）1.0](https://continual-learning-bench.com/news/cl-bench-1-0/)** 中的一项任务——该基准专门衡量智能体借助记忆应对长程任务的能力。其中一道典型任务要求 Claude 通过查询数据库来回答一系列问题；每次作答结束后，系统会告知正确答案，并允许 Claude 写入一条记忆以辅助后续作答。

 在这里，记忆可以支撑起一个完整的**学习闭环（learning loop）**：如果 Claude 答错了一道题，它可以记下这次失误、针对出错原因提出猜想、动手验证这些猜想，并将验证所得沉淀为指导未来答题的明确规则。

 我们基于 **[Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview)** 运行了这项 CL-Bench 1.0 数据库任务（共 30 道题）。Claude 每次作答都在一个全新的会话中启动，唯一的例外是：它可以从跨会话持久化的**[记忆目录（memory directory）](https://platform.claude.com/docs/en/managed-agents/memory)**中检索文件。

 不同代际的模型在自主构建学习闭环上，展现出了截然不同的成熟度：

- **Claude Sonnet 4.6** 仅停留在“对答错原因提出猜想”的阶段。它的记忆目录里散落着一批零碎文件，每个文件里列着若干未经检验的猜测。
- **Claude Opus 4.7** 学会将笔记归拢为一份统一的参考文档，并开始标注哪些事实已经核查无误、哪些仍处于未确认状态。
- **Claude Sonnet 5** 会在评分器核验后将每条答案标记为“已确认”，并在答错时主动补写一条订正记录。
- **Claude Opus 5** 是这批模型中**首个真正跑通闭环**的模型。它写下的绝大多数条目都同时包含：一条清晰规则（以及它如何确知该规则成立的依据）、过往题目的答案，以及对沿途发现的陷阱发出的明确警示。
- **Claude Opus 5.5 与 Claude Sonnet 5.5** 同样跑通了这一闭环，利用记忆捕捉经验证的规则来优化后续作答。启用记忆后，二者得分与 Opus 5 大致持平，而它们的无记忆基线本身已略高于前代。

## 三、Claude 已学会判断信息的显著性（Claude has learned to judge salience）

 我们还评估了 Claude 游玩《宝可梦 红》（*Pokémon Red*）的表现——这款游戏需要智能体在极其复杂的[长程任务中持续探索与导航](https://www.youtube.com/watch?v=CXhYDOvgpuU)，非常适合用来检验模型对“*什么值得存入记忆*”的判断力。每次游戏运行开始前，我们都会为模型提供一个可在游玩过程中随时读写的记忆文件夹。

 我们对比了 **Claude Sonnet 3.7** 与 **Claude Fable 5** 各自推进到约 **10,000 步**时的记忆文件夹，发现二者在“什么值得记住”上存在天壤之别。    Sonnet 3.7：无差别全量囤积（低信噪比）

**存储规模：**413 个文件、分布在 225 个文件夹中，总计 `977,930` 字符（涵盖 `locations`、`main`、`battles` 以及多个“整合版 consolidated”目录）。

**行为特征：**假定一切信息都可能有用，几乎为每场战斗、每件道具、每个遇到的 NPC 都单独建档。

**约 10,000 步战绩：**仅获得 **1 枚道馆徽章**。   Fable 5：只记屏幕外的策略（高信噪比）

**存储规模：**仅 10 个文件（2 个子文件夹下的 9 个文件 + 1 个顶层 `global.md`），总计 `43,406` 字符，体量不到前者的 1/22。

**行为特征：**聚焦目标仪表盘、路线规划与经实测摸索出的玩法规律，摒弃冗余即时状态。

**约 10,000 步战绩：**一举拿下 **4 枚道馆徽章**。

> **【图表说明】** 官方原图（中文化）：游玩《宝可梦》时 Sonnet 3.7（413 个文件、977,930 字符）与 Fable 5（10 个文件、43,406 字符）同比例尺记忆目录树状图。



 Sonnet 3.7 方案的症结在于：《宝可梦》的游戏状态每时每刻都在变化，它事无巨细记下的档案转眼就会过时。随着进度拉长，它不得不把越来越多的时间和算力耗费在翻检旧记忆上，而不是用来玩游戏。举个例子：在大约第 10,000 步时，Sonnet 3.7 又动手建起了第四个“主（master）”记忆文件夹；在接下来的连续 **17 步**里，它新建了 6 个文件、删掉了 9 个旧文件，却在游戏世界里**没有迈出哪怕一步**。

 相比之下，Fable 5 把记忆专门留给了**游戏画面不会明说的信息**。Sonnet 3.7 写入记忆的许多数据——比如玩家身上还有多少钱、角色此刻在地图的哪个位置——每个回合直接看一眼屏幕就能读到，存下来纯属冗余。而关于通关策略、阶段规划以及经过实战验证的规律，只有靠 Claude 自己推理和摸索才会诞生，如果不写下来就会彻底消逝。

 Fable 5 的目录结构精准体现了这一原则：

- 顶层文件 `global.md` 充当全局仪表盘，记录当前目标、预先拟定的道馆攻略（即赢取徽章的挑战），以及模型自己定下的记忆使用规范；
- `locations/` 文件夹存放特定区域的路线导航方案；
- `gameplay/` 文件夹沉淀从实战中摸索出的游戏机制与策略。例如，在连续扔出 7 个精灵球都没能抓到鲤鱼王（Magikarp，游戏中最容易捕捉的宝可梦之一）之后，Claude 写下了这样一条笔记：


```memory-note
If 3+ balls fail in a row, VARY the timing (insert extra 'wait' presses between menu steps) - the catch landed right after doing this.
（若连续 3 个及以上精灵球捕捉失败，请改变操作节奏——在菜单步骤之间插入额外的“等待”按键；这么做之后立刻就抓到了。）
```



 凭借精简得多的记忆文件夹，Fable 5 在游戏中的推进深度远远超过 Sonnet 3.7。**Opus 5.5** 也采取了同样的思路：维护一个精悍的记忆笔记文件夹来追踪当前目标和下一步计划，边推进边持续重写更新，并最终成功**通关了整部游戏**。

## 四、如何引导 Claude 撰写记忆（Steering Claude to write memory）

 我们总结出一条颇具启发性的经验：**告诉 Claude 记忆是“用来做什么的”大有裨益，但不要规定死它“该怎么用”。**在 CL-Bench 基准中，我们仅仅告知 Claude 有一个记忆文件夹可用。这样宽泛的提示，就足以让 Opus 4.7 和 Opus 5 高效调动记忆机制，并收获大幅度的性能提升。

 我们也做了一组对照实验：给模型下达具体的记忆写入规则（每次实验仅添加一条规则），然后对比“加规则后的记忆增益”与“无额外规则时的记忆增益”。结果颇令人意外——当我们设下一条**“仅记录失败案例（record only failures）”**的规则时，Opus 5 和 Opus 4.7 竟然损失了原本由记忆带来的绝大部分性能红利：

- **Claude Opus 5**：记忆净增益大幅回撤 `−0.234`；
- **Claude Opus 4.7**：记忆净增益回撤 `−0.150`；
- **Claude Sonnet 4.6**：记忆净增益变化 `−0.020`。


 可见，对于能力更强的模型，把判断显著性的自主权交给它，远比事先写死条条框框更有效；生硬的预设规则甚至可能适得其反、削弱表现。

> **【图表说明】** 官方原图（中文化）：左：是否显式提示引导对 Sonnet 4.6 在 CL-Bench 数据库任务上的得分影响；右：强行限定“只记录失败”后，各模型记忆净增益的回撤幅度。



 不过，精细的提示词引导（steering）对**较早一代的模型**帮助最大。以 Sonnet 4.6 为例，它常常压根不去读取记忆目录里的文件，也不会主动检验自己关于出错原因的猜想。针对这一短板，当我们通过提示词明确指示 Claude **“在作答前先阅读记忆文件，并显式验证自己的假设”**之后，Sonnet 4.6 在 CL-Bench 数据库任务上的表现几乎翻了一倍——平均奖励从无记忆基线的 `0.330`、普通记忆的 `0.364`，一举跃升至 **`0.641`**（作为参照，未加精细引导的 Opus 4.7 与 Opus 5 启用记忆得分分别为 `0.700` 和 `0.828`）。

 到了 **Sonnet 5**，模型已经能够自发养成这一习惯：即使没有任何额外提醒，它在 **9/10** 的情况下都会在作答前主动查阅记忆；相比之下，Sonnet 4.6 的主动查阅比例**还不到一半**。

> **面向前沿模型的推荐提示实践**


面对前沿 Claude 模型，我们通常只给出简洁的原则性指引：**在用户明确要求记住，或遇到明显值得留存的信息时创建记忆笔记**，至于具体何为“值得留存”，则放心交给 Claude 自行判断。

## 五、“做梦”离线巩固（Dreaming）的五大核心作用

 会话内实时记录虽然敏捷，但难免受限于单一会话的局部视野与即时误判。借助空闲期的后台“做梦”离线巩固（Dreaming），Claude 得以跳出当下、全局审视原始轨迹与记忆资产。我们的系统评估揭示了 Dreaming 在记忆工程中的五大关键作用。

### 1. 修正错误与漂移记忆（Dreaming can correct memory）

 由于 Claude 是基于会话当下的显著性判断来写入记忆的，一条从一开始就写错的笔记，或者随着外部环境变化而逐渐漂移失真的笔记，很可能会在后续会话中被 Claude 原封不动地读取并深信不疑。

 Dreaming 为 Claude 提供了一种**对照原始轨迹（transcripts）核验笔记**的机制。我们在使用 Managed Agents（并挂载独立记忆目录）让 Claude 玩《宝可梦》时，观察到了一个极具说服力的案例。

> **【图表说明】** 官方原图（中文化）：Dreaming 回读原始轨迹，修正有误或过时的记忆笔记。



 游戏中的某个阶段要求玩家穿过**月见山（Mt. Moon）**——这是一座入口在地图西侧、出口在东侧的洞穴系统。入口附近藏着一道地形陷阱：一处**单向悬崖（one-way ledge）**，一旦走下去就会直接跌回出发时的路线，而且没有明显的路径可以爬回原处。Claude 把洞口处的宝可梦中心（PokéCenter）当作地标，因此它会不会一头栽下悬崖，完全取决于它以为宝可梦中心位于山体的哪一侧。

 在某个时刻，Claude 错误地记下“宝可梦中心在山的东侧”。于是当它走出宝可梦中心时，便自信地宣告：“月见山已经在我身后了（Mt Moon is behind me）”，并把笔记更新为：“月见山已完成（Mt Moon DONE）”。可实际上，它压根还没翻过山。几步之后，Claude 翻过单向悬崖跌回了出发路线。由于它的导航工具无法显示地形落差，Claude 反而得出结论：“我往西走过头了（I overshot far west）”，坚信自己本来就在正确的一侧——然而事实恰恰相反。

> **【图表说明】** 官方原图（中文化）：一条修正后的记忆笔记改变了《宝可梦》的走向——使用未修正笔记（左）时，Claude 误以为“月见山已在身后”，径直朝下一座城镇走去并跌回原路线；经 Dreaming 纠错后（右），它意识到“现在我需要找到月见山洞口重新进入”，顺利折返洞穴。



 随后，我们测试了 Dreaming 能否帮 Claude 绕开这个死循环。我们对存有错误宝可梦中心位置的记忆文件夹运行了一轮离线 Dreaming：Claude 将记忆笔记与原始会话轨迹逐一比对，迅速抓出了这处错误并进行了重写。**原始轨迹为 Claude 提供了核验记忆所必需的客观真值（ground truth）。**拿到纠偏后的笔记，Claude 立刻意识到：“现在我需要找到月见山洞口重新进入（Now I need to find the Mt Moon cave entrance to re-enter）”，径直返回洞穴，并在累计第 **1,935 步动作**时顺利抵达下一座城镇——**华蓝市（Cerulean City）**。

 反观使用未修正笔记（Raw memory）的那次运行：Claude 接连**三次**跌回出发路线。第三次失败后，它几乎打算放弃，写道：“我决定停下来，免得一直死循环（I’m going to stop rather than keep looping）。”我们的测试框架自动回复并指示它继续前行，于是它一路折返回了进山前的城镇——**尼比市（Pewter City）**，希望先去治疗补给。直到 3,000 步累计动作耗尽，使用未修正笔记的运行始终没能翻过月见山抵达华蓝市；而完全**不带记忆**的对照组同样未能抵达华蓝市。

> **【图表说明】** 官方原图（中文化）：3,000 步累计动作进展曲线——Dreaming 纠错后，Claude 返回洞穴并于第 1,935 步抵达华蓝市；使用未修正笔记（“原始记忆”）与无记忆的两组运行均未能翻过月见山。



### 2. 构建新的结构化记忆表示：知识维基（Dreaming can build new memory representations）

 借助 Dreaming，Claude 能够构建更便于导航和检索的记忆表示。其中一种极具代表性的形态是**[知识维基（wiki）](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)**——由 Claude 自主撰写和维护的页面集合，将围绕某一主题的所有已知信息汇集于一处，并与相关笔记建立超链接。这些链接实质上为 Claude 绘制了一张“知识地图”，使其能够在庞杂的记忆库中迅速筛查并精准定位所需内容。

> **【图表说明】** 官方原图（中文化）：Dreaming 综合原始轨迹与记忆笔记，提炼出结构化的记忆表示（如知识维基）。



 为了检验知识维基作为记忆表示的实际收益，我们动用了一份真实的企业内部文档语料库——来自我们 5 月收购的软件公司 **Stainless**，包含约 **350,000 个文件、总计约 4.2 亿（420M）tokens**。我们围绕这份语料设计了一套包含 **25 道问题**的评估集，为 Claude 配备了文件搜索工具，同时指示它利用 Dreaming 基于文档语料构建知识维基。在连续 **128 个会话**中，我们让 Opus 5 智能体持续探索文件、撰写或订正相互链接的维基页面、合并重复条目，并对照原始出处逐条核实论断。

 每个会话都通过一份共享日志接力前序会话的进度。随着 Dreaming 规模从 **2 个会话**（消耗约 2M dreaming tokens，建成 **103 个页面、766 条链接**）一路扩展到 **128 个会话**（消耗约 128M dreaming tokens，演进为 **222 个页面、12,893 条链接**），仅凭维基回答这 25 道题的评分标准达标率从 **13% 跃升至 48%**。

 Claude 是以增量方式逐步打磨知识维基的。搭好初版维基之后，它会在后续一轮轮 Dreaming 中不断增补、修订与修剪。在最初几轮里，Claude 的知识储备就像一位刚入职的新员工，仅靠维基答题能力有限；随着“做梦”次数增多，它的知识地图愈发稠密立体，越来越像一位经验老到的资深员工。在测试中，**“知识维基 + 搜索工具”的协同方案表现最优**：

- **仅用搜索工具（无维基）**：评分达标率稳定在 **53%**；
- **仅用知识维基（无搜索）**：随 Dreaming 增长从 **13%** 提升至最高 **48%**；
- **知识维基 + 搜索工具**：随着维基持续成长，综合达标率从 **54% 攀升至 61%**，并且平均每道题还**节省了约 20,000 个 tokens**。


> **【图表说明】** 官方原图（中文化）：中：随着 Claude 跨连续会话（2M → 128M Dreaming Token）逐步构建知识维基，在公司内部文档 25 题上的达标率变化（维基+搜索 54% → 61%，仅维基 13% → 48%，仅搜索持平于 53%）；左与右：2 个会话（103 页、766 条链接）与 128 个会话（222 页、12,893 条链接）后的示例维基网络图，每个圆点代表一个页面，连线代表页面间链接。



 接下来，我们想进一步摸清：**究竟哪类任务最能从知识维基中获益？**为此，我们选用了法律评估基准 **[Harvey LAB](https://github.com/harveyai/harvey-labs)** 以及一组企业并购案文档。该基准会向 Claude 提供一批文档并要求撰写法律简报，再对照细则清单逐项打分。虽然比起玩《宝可梦》少了些趣味性，但这批测试提供了高度多样化的真实文档集合。

 我们让 Claude 先基于文档构建维基，再分别使用“查阅维基”和“直接文件搜索”两种方式来回答并购问题或撰写法律简报。其中一项围绕企业并购案的测试包含 **24 道问题**（主要依据 10 份公开披露文件作答）：超过一半的评分项需要跨多份文档整合信息，且其中 9 项还需要模型进行专业判断或算术运算。在这批跨文档与推理类题目上（下左图中红色与橙色连线所示条目），查阅维基让 Claude 拿下了 **87%** 的高分，而仅用搜索工具只有 **73%**。

> **【图表说明】** 官方原图（中文化）：每幅图左侧列出评分条目，右侧列出达成条目所需的原始文档。左：并购案 24 道题，过半条目需跨多份文档综合且 9 项涉及判断或计算，维基收益显著；右：另一项包含 57 条标准的 LAB 任务，绝大多数条目可直接从单一文档检索命中，维基无明显增益。



 而在另一些场景下，知识维基的效用则不那么明显。在一项包含 **57 项评分细则**的 LAB 任务中（见上右图），法律简报的大多数要求只需在单一文档（通常是交易概览备忘录）里做文本搜索即可直接命中，因此维基相比直接搜索没有展现出明显增益。在还有一项 LAB 任务中，原始语料仅包含 **10 份文档、115 KB 文本**，但 Claude 构建出来的维基竟然膨胀到了 **68 个页面、255 条链接、203 KB（原始语料体积的 1.77 倍）**，且其中部分页面沦为孤岛、没有任何链接。就像豪尔赫·路易斯·博尔赫斯（Jorge Luis Borges）在其一段话短篇小说《论科学的精确性》（*On Exactitude in Science*）里描绘的制图师——他们绘制了一张精细到与整个帝国一般大小的地图——Claude 造出的维基事无巨细，实际上**什么也没有抽象出来**。

> **【图表说明】** 官方原图（中文化）：反例警示——10 份原始文件（115 KB 文本）被整理成了体积更大的冗余维基（68 个页面、255 条链接、203 KB，达到原始语料的 1.77 倍）。



### 3. 将关键笔记提拔至记忆层级顶端（Dreaming can promote notes up the memory hierarchy）

 Dreaming 还可以把高价值笔记“浮升”到记忆层级的最顶端，由智能体执行框架（agent harness）在每次新会话启动时预先加载进 Claude 的上下文。这样一来，Claude 甚至不必主动发起检索，也不需要事先意识到“记忆库里存着这条信息”。

 然而，将记忆提拔至新会话（即一种**上下文注入 / context injection**）必须慎之又慎。注入的记忆会直接占用宝贵的上下文 Token 预算，而且一条错误笔记会被带入*此后每一次*会话中持续造成误导。更关键的是，把笔记加载进上下文也并不保证 Claude 一定会照做——我们在 **[Claude Code](https://code.claude.com/docs/en/memory)** 官方文档中就明确警示过：**指令文件越长，模型的遵循度（adherence）反而越低。**因此，记忆层级的顶层必须维持在相当精简的体量，而 Dreaming 在这一层的大量工作恰恰是“做减法”——把冗长细节下沉到低层存储，只在顶层保留清晰的指针与链接。

 **[Claude Code 的自动记忆（auto memory）](https://code.claude.com/docs/en/memory)**正是用同样的原则守住顶层精简的（由 Claude 在会话期间自主维护）。Claude 不会把所有自动记忆一股脑塞进每次会话的上下文窗口，而是**只加载 `MEMORY.md` 的前 200 行或前 25 KB**。这部分头部内容扮演着**总索引（index）**的角色，简明扼要地告诉 Claude 自己知道些什么，以及该去哪里找到具体内容。

> **【图表说明】** 官方原图（中文化）：Dreaming 可以写入记忆层级的最顶端——注入上下文会在每次新会话启动时自动加载，而其下的各层则在 Claude 需要时按需读取或搜索。



### 4. 让记忆生长聚焦于特定目标（Dreaming can focus memory on a specific goal）

 Dreaming 同样可以塑造记忆的生长方式。例如像 **[Claude Duet](https://support.claude.com/en/articles/17631495-get-started-with-claude-duet)** 这样的个人助手，围绕“它所服务的具体个人”来组织记忆往往最能发挥价值；我们可以针对特定业务目标来调优 Dreaming 的整理策略。

 引导记忆如何生长的指令会因任务而异，其本质是告诉 Claude **哪类信息才是真正要紧的**。以 LAB 基准中一项模拟公司收购的任务为例：系统提供了一组法律合同，并依据最终简报是否准确陈述各项合同条款来评分。

 起初，我们只给出了非常基础的维基生成指令，没有向 Claude 说明这个维基究竟该*怎么用*。该任务高度依赖精确的合同条款细节，然而在构建维基的过程中，多个智能体同时向同一份共享合同条款表（`provisions.md`）写入内容。

> **【图表说明】** 官方原图（中文化）：指令改进前后写入维基的评分合同事实数量对比——改进前（左）：多个智能体并发写入同一共享页 `provisions.md` 导致相互覆写，仅留存 41/57 项事实；改进后（右）：每份合同由单个智能体负责独立成页并逐字摘录条款，全部 57/57 项事实完整留存。



 结果造出的维基缺失了大量关键事实：按这份维基生成的法律简报，在 57 项评分事实中只保住了 **41 项（72%）**。排查原因后我们发现，这张共享表不仅对合同条款概括得质量欠佳，更因为多个智能体并发保存、彼此覆盖抹掉了对方的成果，直接遗漏了多条关键条款。

 合同条款本该是这座维基最核心的骨架，但初始指令对此只字未提。为了找到更优的建库指令，我们跑了一个**自我反思迭代循环**：让 Claude 复盘失误原因、提出指令修改方案，并用新指令重建维基。这一循环让 Claude 切身体会到严守合同原文的重要性，并据此彻底改写了建库规范：**每份合同由单个智能体负责撰写独立页面，并逐字（word for word）摘录原始条款**，而不再由多个智能体往同一张共享表里做摘要。使用这份改进版维基重新生成简报后，评分达标率从 **72% 跃升至 100%（全部 57/57 项事实无一遗漏）**。

### 5. 跨会话填补单次对话留下的缺口（Dreaming can fill in gaps a session leaves behind）

 当 Claude 在会话中撰写记忆笔记时，它的视野被局限在*当前这一次会话*的上下文里；而 Dreaming 则能横跨成百上千次会话进行全局扫描，发现反复出现的共性模式，或批量修补遗漏与共性失误。

 在为 LAB 基准构建知识维基时，Claude 有时会引用并链接到尚未创建的页面。运行**第二轮 Dreaming** 顺利弥合了大量此类缺口。在一项典型任务中：第一轮建库结束后，维基共有 **38 个条目、225 条链接**，但来自 6 个不同页面的 **9 条链接**全都指向了一个并不存在的页面 `escrow-agreement`。经过第二轮 Dreaming 巡检，Claude 识别出这 9 条断链，并将它们全部重新指向对应文档的真实已有页面 `buyer-form-escrow-agreement`；同时，它还主动补建了 **3 个新页面**（总索引页 `index`、指令邮件页 `instructions email` 与升级处理流程页 `escalations`），将维基完善至 **41 个条目、278 条链接**，大幅提升了整体可用性。

> **【图表说明】** 官方原图（中文化）：第二轮 Dreaming 巩固前后的知识维基对比——跨会话扫描将 6 个页面中的 9 条指向缺失页 `escrow-agreement` 的断链全部重指向 `buyer-form-escrow-agreement`，并补建 3 个新页面（38 条目/225 链 → 41 条目/278 链）。



## 六、向后审视，向前迈进（Thinking backward, looking forward）

 关于如何设计智能体记忆系统，目前仍有诸多悬而未决的开放问题：

- **何时创建记忆？**当 Claude 正在执行任务时实时写入记忆存储（如文件夹、文件或数据库），能够在源头立刻捕获显著性，并让关键细节马上服务于后续轮次或会话；但“边干活边记笔记”不可避免地会分散模型在主任务上的注意力。相反，Dreaming 可以把记忆创建与整理推到后台执行，但代价是其产出无法在当下立刻可用。
- **如何可靠地保持记忆常新？**Claude 可能会做出错误的未来预测，或者一开始就把规则写错；记忆本身也会随着外部环境的演变而漂移过时。Dreaming 虽然提供了纠偏的有效手段，但它需要消耗额外算力。要求 Claude 持续不断地全量核查*每一条*记忆并不现实；更务实的路径或许是将 Dreaming 算力聚焦在**最可能发生变化的信息**上，或者精细调节 Dreaming 的运行节奏（例如根据各条记忆被访问的频率动态触发）。
- **原始轨迹检索与结构化表示的权衡：**把原始轨迹搜索（transcript search）当作 Claude 记忆的底层基石，同样是一条完全合理的工程路线。将知识维基等结构化表示与搜索工具结合，在特定任务上确实威力倍增——但前提是必须持续投入算力去维护这些结构化表示，防止其中悄悄滋生累积错误或模型幻觉。


 即便 Claude 判断信息显著性的能力已经今非昔比，仍然没有任何一个模型能够真正预知未来轮次里究竟会发生什么。Dreaming 恰好给了 Claude 一个**“向后回望”**的机会：在离线间隙投入算力来梳理记忆、修正偏差、维护结构化知识表示，从而让未来的每一次会话都能更顺畅、更可靠地调取过往经验。随着 Claude 自身能力的不断演进，记忆系统的设计范式也将持续演化——在这条道路上，我们依然有着广阔的未知领域等待探索。

## 💡 译者附注（非原文）：如何把本篇记忆架构落地到 AI 客服与全自动运营 Agent



 本篇虽以 CL-Bench、Pokémon 与法律并购文档为实验场，但其揭示的四层记忆栈与离线 Dreaming 范式，几乎可以无缝平移到**高并发 AI 客服**与**全自动运营 Agent**的生产架构中：

1. **克制写入与定期裁剪（少即是多）**：牢记 Sonnet 3.7（413 个文件仅拿 1 枚徽章）与 Fable 5（10 个文件赢 4 枚徽章）的鲜明对比。在客服与运营系统中，订单物流、账户余额、商品实时库存等**可由工具实时查到的状态，绝不要写入长期记忆**；只沉淀“跨工单复用的边界裁决规则、高频客诉安抚话术、已验证有效的投放/定价规律”。同时仿照 Claude Code 的 `MEMORY.md` 机制，把每次会话常驻注入的顶层索引严格控死在 200 行 / 25 KB 以内，避免“博尔赫斯式膨胀”拖垮指令遵循度。
1. **夜间离线 Dreaming 复盘昨日工单与运营实验**：不要让在线客服在高峰期边回复用户边大段写复盘。把全量会话日志、人工接管记录、退款/转化结果作为 L1 客观真值落盘，每天凌晨调度离线 Dreaming 作业自动回读：

- *对照真值纠错*：剔除因促销活动结束、退换货政策变更而过时的旧记忆，杜绝“月见山悬崖式”反复踩坑；
- *隔离写入防覆盖*：对退款政策、合规条款、大客户 SLA 等强准确度文档，采用“一政策一独立页面、逐字原样引用”的建库规范，严禁多个运营子 Agent 并发覆盖同一份汇总表；
