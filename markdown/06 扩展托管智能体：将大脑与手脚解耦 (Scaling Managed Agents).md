# 扩展托管智能体：将“大脑”与“手脚”解耦

Scaling Managed Agents: Decoupling the brain from the hands

>   **发布日期：**2026 年 4 月 8 日 **团队：**Anthropic Engineering **作者：**Lance Martin, Gabe Cemaj & Michael Cohen **预计阅读：**约 10 分钟  [查看官方英文原文 ↗](https://www.anthropic.com/research/managed-agents)

 *想要快速上手 Claude Managed Agents，请参阅我们的[官方文档](https://platform.claude.com/docs/en/managed-agents/overview)。*

 Anthropic 工程博客一直围绕着一条主线展开：如何构建高效的智能体，以及如何为长周期任务设计执行框架（harness）。贯穿这些实践的一个核心洞见是：**执行框架本质上编码了我们关于“Claude 目前自己做不到什么”的假设。然而，随着底层模型不断进化，这些假设必须被频繁重新审视，因为它们很快就会过时。**

 举一个直白的例子：在早期工作中，我们发现 Claude Sonnet 4.5 在感知到上下文窗口快满时会过早草率收尾——一种被称为**“上下文焦虑（context anxiety）”**的现象。为此我们在执行框架里专门加上了“上下文重置（context resets）”机制。可当我们把同一套框架换到 Claude Opus 4.5 上运行时，发现这种焦虑已经自行消失——原本辛苦设计的重置逻辑瞬间变成了多余的累赘（dead weight）。

 我们深知执行框架还会持续演变。因此我们构建了 **Managed Agents（托管智能体）**：Claude 平台上的一项托管服务，通过一组精简而稳定的接口替开发者托管运行长周期智能体——这组接口的目标，是**比任何一代具体实现（包括我们今天正在运行的版本）活得更久**。

 构建托管智能体意味着要解决计算机领域的一个古老命题：**如何为“尚未被想象出来的程序”设计系统？**几十年前，操作系统通过将硬件虚拟化为高度通用的抽象——进程（process）、文件（file）——解决了这一难题。这些抽象的寿命远远超过了底层硬件：`read()` 系统调用根本不在乎底层读的是 1970 年代的磁盘组（disk pack）还是现代 SSD；顶层抽象稳如磐石，底层实现得以自由更迭。

 Managed Agents 沿用了完全相同的哲学。我们将智能体的核心组件虚拟化为三个解耦接口：

- **会话（Session）**：只追加写入（append-only）的完整事件日志，记录发生过的一切；
- **执行框架（Harness）**：调用 Claude 并将 Claude 的工具调用路由至相应基础设施的控制循环；
- **沙箱（Sandbox）**：供 Claude 运行代码和编辑文件的执行环境。


 这样一来，任意一个组件的底层实现都可以独立替换，而不惊动其他两层。我们只对这些**接口的形状（interface shape）**定好规矩，而对接口背后具体跑什么实现保持完全开放。

## 一、别把服务器养成了“宠物”（Don't adopt a pet）

 起初，我们把所有智能体组件全都塞进**同一个容器**里——会话状态、执行框架和沙箱共享同一套环境。这种做法有显而易见的好处：文件编辑直接就是本地系统调用，不需要设计跨服务边界。

 但把所有东西耦合进单个容器后，我们立刻撞上了一个经典的基础设施顽疾：**我们养了一只“宠物”**。在运维界著名的**“宠物 vs. 牲畜（pets-vs-cattle）”**隐喻里，“宠物”是起了名字、得小心翼翼照料、绝不能丢的个体；而“牲畜”是完全可互换、坏了随时重建的实例。在耦合架构里，容器服务器成了那只宠物——容器一挂，整个会话就丢了；容器一旦卡死无响应，工程师就得去抢救它。

 抢救卡死的容器意味着去调试卡住无响应的会话。我们当时唯一的观测窗口就是 WebSocket 事件流，但它根本说不清故障究竟出在哪一层：执行框架出 Bug、事件流丢包、或者容器离线，在外面看起来表现完全一模一样。为了查明原因，工程师不得不开 Shell 钻进容器内部排查——可容器里往往存放着用户私有数据，严禁随意侵入，这实际上意味着我们在生产环境几乎丧失了排障能力。

 第二个麻烦随之而来：该框架隐含了一个死假设——“Claude 要操作的一切资源都和它住在同一个容器里”。当企业客户希望让 Claude 连接他们自己的私有云（VPC）时，他们要么得和我们打通网络对等连接，要么得把我们的整套执行框架搬到他们自己环境里部署。**一条被焊死在框架里的隐含假设，在对接异构基础设施时直接变成了绊脚石。**

## 二、将“大脑”与“手脚”解耦（Decouple the brain from the hands）

 我们最终确立的架构方案，是把**“大脑”**（Claude 及其执行框架）与**“手脚”**（实际执行动作的沙箱和工具）以及**“会话”**（持久化事件日志）彻底解耦。三者各自成为几乎不对彼此做假设的独立接口，均可独立容错与替换。

### 1. 执行框架撤出容器，沙箱变成“牲畜”

 解耦后，执行框架不再住在沙箱容器里，而是像调用任意普通工具一样调用容器：`execute(name, input) → string`。容器从此变成了无状态的“牲畜”——如果容器崩溃，执行框架只需把故障捕获为一次工具调用报错返回给 Claude；如果 Claude 决定重试，直接按标准声明 `provision({resources})` 拉起一个全新容器即可，再也不用去抢救坏掉的容器。

### 2. 执行框架本身也变成“牲畜”，故障瞬时恢复

 由于会话日志保存在执行框架外部，框架进程自身不再持有任何需要跨崩溃存活的状态。一旦某个框架实例宕机，只需通过 `wake(sessionId)` 启动一个新实例，调用 `getSession(id)` 拉回事件日志，即可从最后一条事件处无缝续跑。在智能体循环运行期间，框架持续通过 `emitEvent(id, event)` 将事件持久化写入外部会话日志。

### 3. 根治安全边界隐患：让凭证彻底离开沙箱

 在旧的耦合设计里，Claude 生成的不可信代码与认证凭证运行在同一个容器内——提示词注入攻击只需要哄骗 Claude 去读取自己的环境变量就得手了。一旦攻击者拿到这些令牌，就能擅自拉起不受限的新会话去委派恶意任务。收窄令牌权限终究只是权宜之计，因为它暗含了“Claude 拿着受限令牌干不了坏事”的假设——而 Claude 正变得越来越聪明。**真正结构性的根治方案，是确保任何凭证都绝不可能从运行生成代码的沙箱中被触及。**

我们采用两种模式来确保这一隔离——认证信息既可以随资源绑定，也可以存放在沙箱之外的安全保险库中：

- **随资源初始化绑定凭证**：例如对于 Git，我们在沙箱初始化阶段使用各仓库的访问令牌完成克隆并将其绑定到本地 Git 远程配置，使沙箱内可以直接执行 `git push` 和 `git pull`，而智能体全程根本接触不到令牌本身；
- **独立保险库 + 专用代理（Vault & Proxy）**：对于自定义工具，我们支持 MCP 并将 OAuth 令牌存放在沙箱之外的安全保险库中。Claude 通过一台专用代理调用 MCP 工具；该代理接收一个与当前会话关联的令牌，随后从保险库中取出对应的真实凭证并代为调用外部服务——**执行框架自始至终无从知晓任何真实凭证**。


## 三、会话日志 ≠ 模型的上下文窗口（The session is not Claude's context window）

 长周期任务常常远超 Claude 的上下文窗口长度，而常规应对手段几乎都伴随着关于“保留什么”的**不可逆决策**。我们在早前的上下文工程实践中探讨过这些技术：例如，压缩（compaction）让 Claude 保存一份上下文窗口的摘要，而记忆工具（memory tool）让 Claude 将上下文写入文件，从而实现跨会话学习；这些手段还可以与上下文裁剪（context trimming）配合使用，选择性地移除旧的工具返回结果或思考块等 Token。

 然而，选择性保留或丢弃上下文的不可逆决策极易导致失败，因为当下很难预判未来轮次究竟需要哪些 Token。如果消息经过压缩步骤转换，执行框架会将被压缩的消息从 Claude 的上下文窗口中移除，只有当它们被另行存储时才可恢复。此前已有研究尝试通过将上下文作为独立对象存放在上下文窗口*之外*来解决这一问题——例如，将上下文存为 REPL 中的一个对象，让大语言模型编写代码以编程方式对其进行过滤或切片。

> **【图表说明】** 官方原图（中文化）：会话日志作为独立于上下文窗口之外的持久化事件流存在，执行框架通过 `getEvents()` 按需投影上下文。



 在 Managed Agents 中，**外部会话日志（Session）**天然提供了同样优势——它作为一个持久存在于 Claude 上下文窗口之外的上下文对象存在，而不必存放在易失的沙箱或 REPL 进程里。借助 **`getEvents()`** 接口，大脑可以通过选取事件流的位置切片来灵活检索上下文：既可以从上次读到的位置接着读，也可以向某时刻前回溯若干事件以查看前因后果，还可以在执行某项特定操作前重读上下文。

 拉取出的事件在送入 Claude 上下文窗口之前，可以在执行框架内进行任意转换——包括为了实现高提示词缓存（prompt cache）命中率而做的上下文编排，以及各类上下文工程策略。**我们刻意将“在会话层做可恢复的持久化存储”与“在框架层做灵活的上下文管理”拆分开来**，因为我们无法预判未来模型需要哪种具体的上下文工程策略；接口设计把上下文管理下放给可以随时迭代的执行框架，只保证会话日志持久可靠、随时可查。

## 四、多大脑、多手脚（Many brains, many hands）

### 1. 多大脑与首字延迟（TTFT）暴降

 将大脑与手脚解耦，顺带彻底化解了客户最早抱怨的痛点之一：当团队希望让 Claude 操作其私有云（VPC）内的资源时，过去唯一可行的路径就是与我们打通网络对等连接，因为装着执行框架的容器默认所有资源都挨着它放；一旦框架撤出容器，这一隐含假设便不复存在。

 这一重构还带来了惊人的性能红利。过去大脑装在容器里时，“多少个大脑就得先起多少个容器”——对于每一个大脑，在容器制备完成之前都无法开展任何推理，每个会话都得预先支付整套容器冷启动开销。哪怕某些会话自始至终都不会碰沙箱，也必须先克隆仓库、启动进程、再从服务器拉取待处理事件。

 这段白白空转的等待时间直接体现在**首字延迟（time-to-first-token，TTFT）**上——它衡量的是一个会话从接收任务到产出首个响应 Token 之间的等待时长，也是用户体感最敏锐的延迟指标。

 解耦之后，容器仅在真正需要时才由大脑通过工具调用（`execute(name, input) → string`）按需申请。不需要立刻使用容器的会话零等待，编排层一从会话日志拉取到待处理事件即可立刻开始推理。**凭借这一架构，我们的 p50 首字延迟下降了约 60%，p95 延迟更是下降了超过 90%。**扩展到海量大脑只需启动大量无状态执行框架，按需挂载手脚即可。

### 2. 多手脚与跨大脑交接

 我们同样希望每个大脑都能灵活连接“多双手脚”。在实践中，这意味着 Claude 必须在多个执行环境之间进行推理并决定把工作派往何处——这比在单个 Shell 中操作是一项更难的认知任务。早期模型尚不具备这种能力，所以我们才把大脑放进单个容器；随着模型智力跃升，单容器反而成了桎梏：一旦该容器崩溃，大脑伸向各处的所有手脚状态全军覆没。

 彻底解耦后，每一只“手”都被抽象为统一工具接口 `execute(name, input) → string`：传入名称与输入，返回字符串。该接口无缝支持任意自定义工具、任意 MCP 服务器以及我们内置的工具。执行框架根本不知道也不关心沙箱背后究竟是一台容器、一部手机还是一台《宝可梦》模拟器；也正因为没有任何一只手绑死在特定大脑上，**多个大脑之间甚至可以把同一只“手”自由转交给彼此协作。**

## 五、结语（Conclusion）

 我们面对的是那个古老的工程难题：如何为“尚未被想象出来的程序”设计系统。操作系统通过把硬件虚拟化为通用抽象，屹立数十年而不倒；构建 Managed Agents 的初衷如出一辙——打造一套能够从容容纳未来围绕 Claude 出现的各类新执行框架、新沙箱与新组件的底座。

 在这个意义上，Managed Agents 是一套**元框架（meta-harness）**：它不预设未来 Claude 需要哪一种具体执行框架，而是提供足够通用的接口，让多种不同执行框架都能运行其上。例如，Claude Code 是我们在各类任务中广泛使用的优秀执行框架；我们也已经证明，面向特定任务的专用智能体执行框架在垂直细分领域同样表现卓越。Managed Agents 能够兼容上述任意一种形态，并随 Claude 智力的演进持续匹配。

 **元框架设计的核心，在于只对围绕 Claude 的“接口形状”立规矩**：我们笃定 Claude 始终需要操作状态的能力（Session）与执行计算的能力（Sandbox），也始终需要向“多大脑、多手脚”弹性扩展的能力；我们把这些接口打磨得能在长周期内可靠、安全地运转，但绝不对 Claude 未来需要多少个大脑、多少只手、以及它们身在何处做任何僵硬假设。

## 💡 译者附注（非原文）：如何把本篇用到 AI 客服与全自动运营 Agent



- **把客服工单与运营任务流做成“只追加的外部 Session 日志”**：切忌把对话状态绑死在某个 Worker 内存或单一容器里；持久化到外部事件表后，AI 客服实例发版重启、超时重试，甚至把疑难工单从常规路由模型无缝移交给 GPT-6.2 专家大脑，都能按事件游标零丢失续跑。
- **用“独立凭证代理 Proxy”守住生产 ERP 与支付网关**：客服对话和商品评价天然存在恶意提示词注入风险——绝不要把退款 API Key 或数据库密码塞进沙箱环境变量，而是由独立 MCP 代理网关按会话身份从保险库签发代调，并强制校验单笔退款金额上限。
- **按需拉起沙箱，压低纯问答客服的首字延迟**：80% 的物流/政策问答根本不需要代码沙箱，解耦后无状态编排器直接开始推理，只有遇到“核对百笔对账单”或“生成异常报表”时才按需申请临时沙箱，用完即毁。
- **用 Codex 优先固化三大稳定接口契约**：建生产运营平台时，先把 `Session`（事件存储）、`Harness`（编排循环）与 `MCP/Sandbox`（工具执行）之间的接口契约写稳，这样未来从 GPT-6.2 升级下一代模型时，只需替换轻量编排策略而无需推倒重来。
