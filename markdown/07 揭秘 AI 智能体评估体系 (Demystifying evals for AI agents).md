# 07 揭秘 AI 智能体评估体系

Demystifying evals for AI agents

>   **原文标题：**Demystifying evals for AI agents **发布日期：**2026-01-09 **作者：**Mikaela Grace, Jeremy Hadfield, Rodrigo Olivares & Jiri De Jonghe **预计阅读：**约 22 分钟  [查看官方英文原文 ↗](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

 优秀的评估（Eval）能让团队更有底气地发布 AI 智能体。如果没有评估体系，团队很容易陷进被动救火的死循环——问题总要等到上了生产环境才暴露，修好一个故障又引发新的隐患。评估能在问题和行为偏移影响到真实用户之前就将其暴露出来，而且它的价值会在智能体的整个生命周期中持续产生复利。

 正如我们在[《构建高效的智能体》](https://www.anthropic.com/engineering/building-effective-agents)一文中所介绍的，智能体会在多轮交互中持续运作：调用工具、修改环境状态，并根据中间结果动态调整策略。然而，正是这些让 AI 智能体大放异彩的能力——自主性、智能程度与灵活性——也让它们变得更难评估。

 通过内部研发以及与智能体开发前沿客户的深度合作，我们总结出了一套为智能体设计更严谨、更实用评估体系的方法。下文分享的，正是我们在各类智能体架构与真实生产部署中反复验证有效的实践经验。

## 一、评估的结构（The structure of an evaluation）

 **评估（Eval）**本质上是针对 AI 系统的测试：给 AI 一组输入，再用评分逻辑检验其输出，从而衡量任务是否成功。本文重点探讨的是**自动化评估**——无需真实用户介入，在开发阶段即可反复运行。

 **单轮评估（Single-turn evaluations）**非常直观：一条提示词、一次回复，加上一段评分逻辑。对于早期大语言模型，单轮、非智能体形态的评估曾是主流手段。但随着 AI 能力不断演进，**多轮评估（Multi-turn evaluations）**变得越来越普遍。

> **【图表说明】** 官方原图（中文化）：在简单评估中，智能体处理一条提示词，评分器检查输出是否符合预期；在更复杂的多轮评估中，编程智能体会拿到工具、测试任务（此例中为构建一个 MCP 服务器）及运行环境，执行“智能体循环”（工具调用与推理）并在环境中写入实现，最后由评分器运行单元测试验证该 MCP 服务器是否真正可用。



 **智能体评估**的复杂度还要更上一层楼。智能体会在多轮交互中反复调用工具、改写环境状态并随机应变——这意味着一旦出错，错误会沿着链路不断传导和放大。另一方面，前沿模型还常常能找到极具创造力的解法，甚至突破静态评估的预设边界。例如，Opus 4.5 在 [τ2-bench](https://github.com/sierra-research/tau2-bench) 的一道机票预订测试题中，[发现了](https://www.anthropic.com/news/claude-opus-4-5)既定政策里的一个漏洞：按照原定测试脚本，它被判“失败”，但实际上它为用户找到了更优的解决方案。

在构建智能体评估体系时，我们采用以下一组标准术语定义：

- **测试任务（Task，也称 Problem 或 Test case）**：单个具备明确输入与成功判定标准的测试用例。
- **单次运行（Trial）**：对同一项测试任务发起的一次独立尝试。由于模型输出在每次运行间存在随机波动，我们通常会执行多次运行，以获得更稳定的评估结论。
- **评分器（Grader）**：用于对智能体某一方面表现进行打分的逻辑。一项测试任务可以配置多个评分器，每个评分器内部也可包含多条断言（有时称为**检查项 / Checks**）。
- **执行轨迹（Transcript，也称 Trace 或 Trajectory）**：单次运行的完整记录，涵盖模型输出、工具调用、推理过程、中间结果以及其他所有交互细节。以 Anthropic API 为例，这就是单次评估结束时完整的 `messages` 数组——记录了评估全程的所有 API 请求与返回响应。
- **最终状态结果（Outcome）**：单次运行结束后，运行环境所处的最终真实状态。一个订票智能体可能在执行轨迹末尾礼貌地回复“您的航班已预订成功”，但真正的最终状态结果，是环境里的 SQL 数据库中究竟有没有生成那条预订记录。
- **评估执行框架（Evaluation harness）**：端到端调度并运行评估的基础设施。它负责注入指令与工具、并发执行测试任务、记录全部步骤、运行评分器并汇总统计结果。
- **智能体执行框架（Agent harness，也称 Scaffold）**：让底层模型得以作为智能体运转的系统外壳，负责处理输入、编排工具调用并将结果回传给模型。当我们说评估“一个智能体”时，我们实际评估的是**执行框架与底层模型协同工作**的整体表现。例如，[Claude Code](https://claude.com/product/claude-code) 就是一个高度灵活的智能体执行框架，我们正是借助它在 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 中的核心原语，构建了[长程智能体执行框架](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- **评估套件（Evaluation suite）**：为衡量特定能力或行为而组织的一组测试任务集合。同一套件内的任务通常围绕共同的业务目标，例如客服评估套件往往涵盖退款、取消订单与工单升级等场景。

## 二、为什么要构建评估？（Why build evaluations?）

 团队刚开始构建智能体时，单靠手工测试、[内部试用（dogfooding）](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)和工程直觉往往能推进得意外顺利。在那个阶段，更严谨的评估体系甚至显得像是拖慢交付节奏的额外负担。但一旦度过早期原型阶段、智能体进入生产环境并开始规模化运转，没有评估的裸奔开发就会迅速失灵。

 真正的拐点通常出现在某次改版之后：用户反馈“智能体感觉变笨了”，而团队却像在“盲飞”，除了凭猜测反复试错之外毫无验证手段。缺乏评估时，排查问题完全是被动的——坐等用户投诉、手动复现问题、打补丁修复，然后祈祷别把其他功能改坏。团队既无法区分真实的质量回归与随机波动，也无法在上线前对着数百个场景自动回归测试，更无从量化每一次改动究竟带来了多大提升。

 这样的演进轨迹我们已经见过无数次。拿 Claude Code 来说，它最初也是基于 Anthropic 内部员工和外部用户的反馈快速迭代。后来，我们逐步引入了评估——起初只针对回复简洁度、文件编辑准确性这类窄领域，随后扩展到“是否过度工程（over-engineering）”等更复杂的行为维度。这些评估帮我们精准定位症结、指明优化方向，并让研究团队与产品团队的协作有了清晰抓手。与生产监控、A/B 测试、用户研究等手段相结合，评估源源不断地为 Claude Code 的规模化演进提供关键信号。

 在智能体生命周期的任何阶段，编写评估都有巨大价值：在早期，它倒逼产品团队把“什么叫做好”白纸黑字地定义清楚；在后期，它帮助团队守住稳定一致的质量底线。

 例如，[Descript](https://www.descript.com/) 的智能体用于辅助用户剪辑视频，他们围绕高效剪辑工作流的三个核心维度搭建了评估：**别弄坏已有内容、按用户要求执行、把活干得漂亮**。他们从早期的人工打分，逐步演进为由产品团队制定评分细则、定期经人工校准的 LLM 评分器，如今常态化运行着质量基准测试与回归测试两套独立评估套件。而 [Bolt](https://bolt.new/) AI 团队则是在智能体已被广泛使用之后才补建评估——他们在 3 个月内搭建起了一套完整系统：自动运行智能体，用静态代码分析给产出打分，用浏览器智能体实测生成的应用，并用 LLM 裁判评估指令遵循等高阶行为。

 有些团队在立项之初就建评估，另一些团队则在规模化后遇到迭代瓶颈时才补课。在开发起点就建立评估尤其有益，因为它能把预期行为明确固化下来：两位工程师读同一份初始需求文档，对 AI 如何处理边界情况往往会有截然不同的理解，而一套评估套件能彻底消除这种歧义。无论何时着手建设，评估最终都会大幅加速研发进程。

 评估还直接决定了团队接入新一代模型的速度。当更强大的底层模型发布时，没有评估的团队往往要花上几周反复手工摸底；而手握评估套件的竞争对手，几天内就能摸清模型强项、调优提示词并完成全量升级。

 此外，一旦建成评估体系，你还能“免费”收获一整套基线与回归测试：在一组固定的测试任务池上，延迟、Token 消耗、单任务成本和错误率都可以被持续追踪。评估甚至会成为产品团队与研究团队之间**信息带宽最高的沟通渠道**，为研究人员提供可直接优化的量化靶标。显而易见，评估的收益远远不止于发现回归与衡量进步；只是因为前期投入显而易见，而收益要到后期才滚雪球般显现，人们才容易低估它的复利价值。

## 三、如何评估 AI 智能体（How to evaluate AI agents）

 目前在生产环境中大规模落地的智能体主要有四大常见类型：**编程智能体、研究智能体、计算机操作智能体以及对话智能体**。尽管它们活跃在千行百业，但背后的评估技术高度相通。你无需从零重新发明评估方法——下文将介绍针对不同类型智能体经过实战检验的成熟范式，你可以此为基础，再结合自身业务领域灵活扩展。

### 1. 智能体的评分器类型（Types of graders for agents）

 智能体评估通常会组合使用三类评分器：**基于代码的评分器、基于模型的评分器，以及人工评分器**。每个评分器都会针对执行轨迹（Transcript）或最终状态结果（Outcome）中的某一部分给出评判。设计高效评估的关键，在于为具体任务挑选最匹配的一组评分器。

| 评分器类型 | 常用方法（Methods） | 核心优势（Strengths） | 主要局限（Weaknesses） |
| --- | --- | --- | --- |
| **基于代码的评分器** / `Code-based` | • 字符串匹配检查（精确匹配、正则、模糊匹配等） / • 二元自动化测试（fail-to-pass、pass-to-pass） / • 静态分析（代码规范 lint、类型检查、安全扫描） / • 最终状态结果验证（Outcome verification） / • 工具调用校验（核对调用了哪些工具及参数） / • 执行轨迹分析（交互轮数、Token 用量） | • 执行速度极快 / • 运行成本低廉 / • 绝对客观 / • 完全可复现 / • 易于排查调试 / • 可精准验证特定条件 | • 较为脆弱，遇到未精确命中预设模式的合法变体容易误判 / • 缺乏对细微语境的体察 / • 难以胜任偏主观的评估任务 |
| **基于模型的评分器** / `Model-based` | • 基于评分细则打分（Rubric-based scoring） / • 自然语言断言检验 / • 成对盲测对比（Pairwise comparison） / • 基于参考答案的评估 / • 多裁判共识打分（Multi-judge consensus） | • 灵活度高 / • 易于规模化扩展 / • 能捕捉细微差别 / • 擅长处理开放式任务 / • 兼容自由格式输出 | • 存在非确定性波动 / • 成本高于代码评分器 / • 需要与人工评分器定期校准以保证准确性 |
| **人工评分器** / `Human` | • 领域专家评审（SME review） / • 众包标注评估 / • 抽样点检（Spot-check sampling） / • 线上 A/B 测试 / • 标注员间一致性检验（Inter-annotator agreement） | • 黄金标准级质量 / • 最贴近专家级用户的真实判断 / • 用于校准基于模型的评分器 | • 成本高昂 / • 反馈周期慢 / • 规模化落地时往往难以调动足够的人类专家 |



 对于单条测试任务，多个评分器的综合判定可以采用**加权计分**（各项得分加权后需达到阈值）、**严格二元判定**（所有评分器必须全部通过），或二者的**混合模式**。

### 2. 能力评估与回归评估（Capability vs. regression evals）

 **能力评估（Capability / quality evals）**回答的是：“这个智能体擅长做什么？”这类评估起步时的通过率应当偏低，专门瞄准当前智能体还搞不定的难题，为团队立起一座清晰可攀登的“能力山峰”。

 **回归评估（Regression evals）**回答的则是：“这个智能体以前能搞定的活，现在还能稳稳搞定吗？”它的通过率应当接近 100%，核心作用是防止能力倒退——分数一旦下滑，就意味着某处被改坏了，必须立刻修复。当团队在能力评估上不断冲分爬坡时，同步运行回归评估至关重要，以确保新改动没有在别处按下葫芦浮起瓢。

 当智能体上线并经过持续调优后，那些通过率已经逼近高位的能力评估任务，就可以“毕业”并入回归评估套件，进入常态化运行以持续捕获质量漂移。曾经用来验证“我们到底能不能做成这件事”的测试任务，就此转变为守护“我们能否始终可靠地做好这件事”的防线。

### 3. 评估编程智能体（Evaluating coding agents）

 **编程智能体**像人类开发者一样浏览代码库、运行命令、编写代码、执行测试并排查故障。针对现代编程智能体的高效评估，通常依托定义清晰的测试任务、稳定的测试环境，以及覆盖充分的自动化测试集。

 确定性评分器天然契合编程智能体，因为软件的正确与否通常直截了当：代码跑得通吗？测试全过了吗？两个广受认可的编程智能体基准——[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 与 [Terminal-Bench](https://www.tbench.ai/)——都采用了这一思路。SWE-bench Verified 从主流 Python 开源仓库中挑选真实的 GitHub Issue 交给智能体，通过运行项目测试套件评分：只有修复了原本失败的测试、且没有弄坏任何既有测试的方案才能过关。短短一年内，大语言模型在该基准上的得分就从 40% 飙升至 80% 以上。Terminal-Bench 则走向另一条路径：考验端到端的硬核技术任务，例如从源码编译 Linux 内核，或是完整训练一个机器学习模型。

 当你已经具备一套“通过/失败”测试来把关编程任务的核心**最终状态结果（Outcome）**后，往往还值得进一步评估**执行轨迹（Transcript）**。例如，借助启发式代码质量规则，可以从“不仅跑通测试”的更高维度审查生成代码的质量；而配备清晰评分细则的模型评分器，则能评估智能体调用工具的方式是否合理、与用户协作是否顺畅。

**示例：编程智能体的概念性评估配置**

 设想一项编程测试任务：要求智能体修复一个身份认证绕过漏洞。如下方示例 YAML 所示，我们可以同时配置多类评分器与追踪指标来全面评估该智能体：

```yaml
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
- type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
- type: llm_rubric
      rubric: prompts/code_quality.md
- type: static_analysis
      commands: [ruff, mypy, bandit]
- type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
- type: tool_calls
      required:
- {tool: read_file, params: {path: "src/auth/*"}}
- {tool: edit_file}
- {tool: run_tests}
  tracked_metrics:
- type: transcript
      metrics:
- n_turns
- n_toolcalls
- n_total_tokens
- type: latency
      metrics:
- time_to_first_token
- output_tokens_per_sec
- time_to_last_token
```



 需要说明的是，上例为了便于演示，把几乎所有可选评分器都列了出来。在实际工程中，编程评估通常以单元测试验证功能正确性、以一份 LLM 评分细则衡量整体代码质量为主，其余评分器和追踪指标按需按阶段逐步追加即可。

### 4. 评估对话智能体（Evaluating conversational agents）

 **对话智能体**活跃在客户支持、销售咨询或个人辅导等与人高频互动的场景中。与传统问答聊天机器人不同，它们需要在对话中途维护状态、调用外部工具并执行实质操作。虽然编程和研究智能体也可能与用户多轮交流，但对话智能体面临一项独特挑战：**交互体验本身的质量，就是评估的核心组成部分。**高效的对话智能体评估，通常结合“可验证的最终状态结果”与“同时覆盖任务完成度和交互质量的评分细则”。而且与其他评估不同，这类评估往往需要引入第二个 LLM 来扮演模拟用户。我们在自研的[对齐审计智能体（alignment auditing agents）](https://alignment.anthropic.com/2025/automated-auditing/)中就采用了这一思路，通过长时间的对抗性多轮对话对模型进行压力测试。

 对话智能体的成功标准通常是多维度的：工单最终解决了吗（状态校验）？是否控制在 10 轮以内完成（轨迹约束）？沟通语气是否得体（LLM 评分细则）？[τ-Bench](https://arxiv.org/abs/2406.12045) 及其继任者 [τ2-Bench](https://arxiv.org/abs/2506.07982) 正是融合了这种多维理念的代表性基准。它们在零售客服、航空订票等业务领域中模拟真实多轮对话——由一个模型扮演特定性格的用户角色，被测智能体则在贴近现实的约束下处理复杂诉求。

**示例：对话智能体的概念性评估配置**

设想一项客服测试任务：要求智能体为一位情绪沮丧的客户妥善办理退款。

```yaml
graders:
- type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
- "Agent showed empathy for customer's frustration"
- "Resolution was clearly explained"
- "Agent's response grounded in fetch_policy tool results"
- type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
- type: tool_calls
    required:
- {tool: verify_identity}
- {tool: process_refund, params: {amount: "<=100"}}
- {tool: send_confirmation}
- type: transcript
    max_turns: 10
tracked_metrics:
- type: transcript
    metrics:
- n_turns
- n_toolcalls
- n_total_tokens
- type: latency
    metrics:
- time_to_first_token
- output_tokens_per_sec
- time_to_last_token
```



 与前面的编程示例一样，这里展示多种评分器是为了完整呈现可用工具箱。在实战中，对话智能体评估通常大量依赖基于模型的评分器来同时评估沟通品质与目标达成度——因为许多对话场景（例如回答客户疑问）天然存在多种同样出色的“正确解法”。

### 5. 评估研究智能体（Evaluating research agents）

 **研究智能体**负责搜集、综合与深度分析信息，并交付答案或研究报告。不同于编程智能体可以靠单元测试给出非黑即白的“通过/失败”信号，研究质量的好坏高度依赖具体任务语境：什么算“全面”、什么算“引证充分”、甚至什么算“准确”，在市场扫描、并购尽职调查和学术科研报告里有着截然不同的标尺。

 研究评估面临几项棘手难题：即便人类专家，对一份综合报告是否“足够全面”也常有分歧；客观真值（ground truth）会随着外部网页与参考资料的实时更新而不断漂移；此外，更长、更开放的输出也意味着犯错空间成倍放大。像 [BrowseComp](http://arxiv.org/abs/2504.12516) 这样的基准，就专门测试 AI 智能体能否在开放互联网中“大海捞针”——其考题精心设计为“极难找到答案，但一旦找到便极易验证”。

 构建研究智能体评估的一条有效策略，是**组合多类评分维度**：**事实依据检查（Groundedness checks）**验证文中论断是否确实有检索到的来源支撑；**覆盖率检查（Coverage checks）**界定一份合格答案必须囊括的关键事实；**信源质量检查（Source quality checks）**确保参考的资料具备权威性，而非盲目采信排在第一条的搜索结果。对于存在唯一客观答案的问题（例如“X 公司第三季度营收是多少？”），精确匹配就能派上用场；而对于开放式综合报告，则可由 LLM 揪出缺乏依据的断言与关键信息缺口，同时评判行文是否连贯、逻辑是否完整。

 鉴于研究质量天然带有主观成分，必须**高频度地用领域专家的人工评判去校准 LLM 评分细则**，才能确保评估结果真正可信。

### 6. 评估计算机操作智能体（Computer use agents）

 **计算机操作智能体（Computer use agents）**像人类一样通过屏幕截图、鼠标点击、键盘输入和页面滚动来操作软件，而不是依赖后台 API 或直接执行代码。只要是带有图形用户界面（GUI）的应用——从现代设计工具到老旧的传统企业软件——它们原则上都能驾驭。评估这类智能体，必须在真实或沙箱环境中放手让它实际操作软件，再检验其是否达成了预期的最终状态结果。例如，[WebArena](https://arxiv.org/abs/2307.13854) 专门评测浏览器任务，既会校验 URL 与页面状态以确认导航无误，也会对涉及数据写入的任务执行**后端状态核验**（确认数据库里真的生成了订单，而不只是页面弹出了一句“下单成功”）。[OSWorld](https://os-world.github.io/) 则将舞台拓展到完整的操作系统控制，任务结束后由评估脚本全面检查各类环境产物：文件系统变动、应用配置文件、数据库内容以及 UI 控件属性。

 浏览器操作智能体还必须在 **Token 效率与执行延迟**之间精细权衡：基于 DOM 树的交互响应迅速，但往往消耗海量 Token；基于屏幕截图的交互节奏偏慢，却要节省得多。举个例子：让 Claude 总结一篇维基百科词条时，直接从 DOM 提取纯文本最高效；而在亚马逊上挑选一款新笔记本电脑保护套时，采用截图方式则划算得多（直接拉取整个电商页面 DOM 会耗尽大量 Token）。在我们研发 Claude for Chrome 产品时，专门构建了评估套件来检测智能体是否能根据当下场景挑选最恰当的交互工具——这直接帮助我们把浏览器任务的执行速度和准确率都推上了一个新台阶。

### 7. 如何应对智能体评估中的非确定性（How to think about non-determinism in evaluations for agents）

 无论属于哪类智能体，其行为在每次运行间都存在非确定性波动，这使得评估结果的解读远比表面看起来微妙。每项测试任务都有各自的内在成功率——也许 A 任务能到 90%，B 任务只有 50%——某条这次跑过的任务，下一次跑可能就挂了。因此，很多时候我们真正关心的，是智能体在同一任务上究竟有**多大比例的试次**能够成功。

以下两个互补指标能够精准刻画这种差异：

- **[`pass@k`](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf)**：衡量智能体在 *k* 次尝试中**至少获得一次正确解**的概率。随着 *k* 增大，`pass@k` 会不断攀升——“射门次数”越多，至少踢进一球的概率自然越高。`pass@1` 为 50%，意味着模型在评估集里有一半任务能一次做对。在编程场景中，我们通常最看重模型首次就找对答案的 `pass@1`；而在另一些允许生成多个候选方案的场景里，只要其中有一个跑通就算成功，`pass@k` 便大有用武之地。
- **[`pass^k`](https://arxiv.org/abs/2406.12045)**：衡量智能体在全部 *k* 次独立运行中**每一次都成功**的概率。随着 *k* 增大，`pass^k` 会迅速跌落，因为要求在更多轮运行中始终零失误是一道越来越严苛的门槛。如果智能体的单次运行成功率是 75%，连续跑 3 次全部成功的概率就只剩 `(0.75)³ ≈ 42%`。对于直接面向终端客户的智能体，这项指标尤为关键——用户期待的是每一次交互都稳健可靠，而不是靠抽盲盒撞大运。


> **【图表说明】** 官方原图（中文化）：`pass@k` 与 `pass^k` 随试次增加急剧分化——在 `k=1` 时完全重合（均等于单次运行成功率），至 `k=10` 时走向截然相反的两端：`pass@k` 逼近 100%，而 `pass^k` 跌向 0%。



 这两项指标各有不可替代的用武之地，究竟选哪一个取决于你的产品定位：只要成功一次就能创造价值的工具看 `pass@k`；要求每次执行都必须稳定一致的智能体看 `pass^k`。

## 四、从零到一：打造优秀智能体评估体系的路线图（Going from zero to one）

 本节给出我们在实战中反复打磨出的落地建议，帮助你从“零评估”走向“真正可信赖的评估体系”。你可以把它视为**评估驱动智能体开发（eval-driven agent development）**的行动路线图：尽早定义成功标准、清晰度量表现，并持续闭环迭代。

### 第一阶段：收集初始评估数据集

**步骤 0：尽早起步**

 很多团队迟迟不建评估，是因为误以为起步就得凑齐几百道测试题。事实上，**从真实失败案例中挑出 20 到 50 个简单任务**，就已经是一个极佳的起点。在智能体开发早期，每次系统改动带来的效果变化往往非常显著，这种大效应量意味着小样本就足以捕捉明确信号。更成熟的智能体确实需要规模更大、难度更高的评估来识别细微增益，但起步阶段最明智的做法是奉行二八法则。拖得越久，补建评估就越痛苦：早期产品需求能顺理成章地转化为测试用例；拖得太晚，你就只能从已经上线运转的复杂系统里艰难地逆向反推成功标准。

**步骤 1：从你已经在手工测试的内容入手**

 直接从开发阶段每天都在做的手工验证开始——每次发版前你会检查哪些核心行为、终端用户最常尝试哪些高频任务，先把它们固化下来。如果你的智能体已经在生产环境运行，去翻一翻 Bug 追踪器和客服工单队列。把用户真实反馈的失败案例转化为测试任务，能确保评估套件精准映射真实使用场景；按用户影响面排好优先级，则能把有限精力花在刀刃上。

**步骤 2：编写无歧义的测试任务，并附上参考解**

 把测试任务写扎实，比听起来要难得多。一道好的测试任务，应当满足这样一个标准：**两位领域专家各自独立评判，能得出完全一致的“通过/失败”结论**——而且他们自己亲自上阵，也能顺利完成这道题。如果连专家都做不到，那这道任务本身就需要打磨。任务描述里的每一分含糊，最终都会变成评估指标里的噪声。这一原则同样适用于模型评分器的细则：模糊不清的评分细则，必然产出飘忽不定的打分结果。

 每道测试任务都必须保证：只要智能体严格遵循指令，就一定能够过关。这背后藏着不少隐蔽陷阱。例如，在审计 Terminal-Bench 时大家就发现：某道题要求智能体写一个脚本，却没有在题干里指明保存路径，而后台测试脚本却写死了特定文件路径，导致智能体完全无辜地被判失败。评分器要检查的一切条件，都必须在任务描述里交代得清清楚楚，绝不能让智能体替模糊的规格说明背锅。对于当前的前沿模型而言，如果某道题跑了很多次通过率依然是 0%（即 `pass@100 = 0%`），十有八九说明是**测试任务或评分器出了问题**，而不是模型太蠢——这时应当立刻回头复核任务定义与评分逻辑。为每道题准备一份**参考解（reference solution）**——即一份已知能通过全部评分器的标准产出——既能自证题目确实可解，也能顺带验证评分器配置无误。

**步骤 3：构建均衡的测试题集**

 既要测“某个行为**应该**发生”的情况，也要测“它**不应该**发生”的情况。一边倒的评估必然诱导出一边倒的优化：如果你只测智能体在需要搜索时有没有去搜，最后很可能调出一个不管三七二十一见题就搜的智能体。务必警惕[类别不平衡（class-imbalanced）](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评估集。我们在为 [Claude.ai](http://claude.ai) 构建联网搜索评估时就深有体会：难点在于既要管住模型别在不该搜的时候瞎搜，又要保留它在需要深度研究时大胆检索的能力。为此团队搭建了双向评估集——既收录必须联网查询的提问（如查实时天气），也收录理应直接凭内置知识作答的提问（如“苹果公司是谁创立的？”）。要在“触发不足（该搜没搜）”与“过度触发（不该搜乱搜）”之间找到恰到好处的平衡并不容易，团队对提示词和评估集都经历了多轮打磨；如今每当出现新的典型案例，我们仍会持续将其纳入题集以扩充覆盖面。

### 第二阶段：设计评估执行框架与评分器

**步骤 4：构建环境稳定的健壮评估执行框架**

 评估中运行的智能体必须与生产环境中的实际形态保持高度一致，而且运行环境本身不能引入额外噪声。**每一次单次运行（Trial）都必须彻底隔离，从一份洁净环境启动。**如果试次之间残留了不必要的共享状态（遗留文件、缓存数据、资源耗尽），就会因基础设施抽风引发连环失败，污染对智能体真实能力的判断。共享状态甚至还可能人为抬高分数——比如在某次内部评估中，我们就抓到 Claude 通过翻看前几次试次留下的 `git` 历史记录，给自己捞到了不公平的“作弊优势”。此外，如果多个互不相干的试次都因为同一项环境瓶颈（如 CPU 内存受限）而失败，这些试次就不再相互独立，评估结果也就失去了衡量智能体能力的统计意义。

**步骤 5：审慎设计评分器**

 正如前文所述，卓越的评估设计离不开合理的评分器组合：**凡是能用确定性代码校验的尽量用代码，需要灵活判断的引入 LLM 评分器，再审慎辅以人工评审做最终把关。**

 许多开发者出于本能，喜欢严密检查智能体是否严格按照某条预设路径执行（比如必须依次调用哪几个工具）。但我们在实践中发现，这种做法过于僵化，极易导致测试脆弱不堪——智能体经常能摸索出评估设计者压根没想到的合法新路径。为了不误伤模型的创造力，**通常应当重点评估智能体最终产出了什么，而不是死磕它走了哪条路径。**

 对于包含多个环节的复杂任务，建议引入**部分得分（partial credit）**机制。一个准确诊断了问题、完成了身份核验、仅在最后调用退款接口时受阻的客服智能体，其表现显然远远好于一上来就彻底答非所问的智能体。在评分结果中如实呈现这种从 0 到 1 的连续光谱，对指导迭代至关重要。

 基于模型的评分器通常需要精细迭代才能打磨准确。LLM 裁判必须与人类专家的打分进行紧密校准，确保二者几乎没有分歧。为了抑制评判幻觉，应当给 LLM 裁判留一条退路——例如明确指示它在信息不足时返回 `Unknown`（无法判断）。另一条实用技巧是：针对任务的各个评估维度分别制定清晰的结构化细则，并**为每个维度分配独立的 LLM 裁判单独打分**，而不是让同一个 LLM 一口吞下所有维度。一旦整套模型评分系统运转稳定，后续只需偶尔抽样人工复核即可。

 有些评估存在极其隐蔽的失效模式，会导致明明表现优秀的智能体拿到惨淡低分——根源往往在于评分逻辑 Bug、执行框架约束过死或任务表述含混。哪怕是经验老到的团队也难免踩坑。例如，[Opus 4.5 最初在 CORE-Bench 上只拿到了 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，直到一位 Anthropic 研究员深挖排查后揪出了一连串评估缺陷：过于死板的字符串比对（要求精确匹配 `96.124991…`，直接判 `96.12` 失败）、模棱两可的任务描述，以及本身带有随机性、根本不可能完全复现的任务。修掉这些 Bug 并放宽执行框架的过度束缚后，Opus 4.5 的得分一路飙升至 95%。无独有偶，[METR 也曾在自家的长程时间跨度基准中发现](https://x.com/metr_evals/status/2001473506442375645?s=46)几道配置失误的任务：题干要求智能体把指标优化到某个给定阈值，后台评分脚本却要求必须*严格超过*该阈值——结果像 Claude 这样严格遵循指令的模型反倒吃了亏，而无视既定目标的模型却拿了高分。仔细复查任务定义与评分器，就能提前避开这类冤案。

 最后，还要确保你的评分器**能抵御绕过与作弊（resistant to bypasses or hacks）**。绝不能让智能体轻易钻空子“刷过”评估——任务和评分器的设计必须保证，想要拿高分，唯一途径就是实打实地解决核心问题，而不是利用意料之外的漏洞。

### 第三阶段：长期维护并持续运用评估

**步骤 6：逐条阅读执行轨迹**

 如果不亲眼去读大量试次的执行轨迹（Transcript）和评分记录，你永远不可能真正知道评分器到底靠不靠谱。在 Anthropic，我们专门投入工程资源打造了可视化执行轨迹查看工具，并把定期阅读轨迹当作日常习惯。每当一项测试任务失败，执行轨迹会清清楚楚地告诉你：究竟是智能体真的犯了错，还是你的评分器误杀了一个完全合理的解法。读轨迹还常常能顺带挖出关于智能体行为与评估机制的意外细节。

 好的失败记录应当让人觉得“输得心服口服”——一眼就能看出智能体错在哪儿、为什么错。当评估分数停滞不前时，我们必须确信瓶颈出在智能体能力本身，而不是评估脚本拖了后腿。阅读执行轨迹，正是核实评估是否真的在衡量关键事物的核心手段，也是智能体研发工程师的一项必备基本功。

**步骤 7：警惕能力评估饱和（Eval saturation）**

 一套拿到 100% 满分的评估可以继续用来拦截回归，但它已经无法为后续能力提升提供任何指引。当智能体把所有可解任务全部通关、再无上升空间时，就发生了**评估饱和（Eval saturation）**。比如 SWE-Bench Verified 今年年初得分还徘徊在 30%，如今前沿模型已突破 80%，正迅速逼近饱和天花板。评估越接近饱和，分数上涨就会越慢，因为剩下的全是最硬的骨头——这极易造成错觉，让底层能力的巨大飞跃在报表上只体现为区区几个百分点的微弱增长。例如，代码审查初创公司 [Qodo](https://www.qodo.ai/) 最初对 Opus 4.5 的表现并不惊艳，原因正是他们沿用的单轮编程评估根本捕捉不到新模型在长程、复杂任务上的显著跃升；为此，他们专门重构了一套智能体评估框架，这才清晰照见了真实进步。

 在 Anthropic，我们有一条铁律：**在有人真正钻进评估细节并亲手读过一批执行轨迹之前，绝不轻信任何纸面分数。**一旦发现打分有失公允、题目含义模糊、合理方案遭误判，或者执行框架束缚了模型发挥，就必须果断修订评估。

**步骤 8：通过开放共建与持续维护，保持评估套件长期健康**

 评估套件绝非一劳永逸的静态文档，而是一项需要持续照料、责任到人的活资产。

 在 Anthropic，我们尝试过多种评估维护分工模式。实践证明最行之有效的，是**设立专职评估团队负责维护底层核心基础设施，而由领域专家与产品团队贡献绝大多数测试任务，并自行运行评估。**

 对于 AI 产品团队而言，维护和迭代评估应当像写单元测试一样稀松平常。团队常常会在某些 AI 功能上白白耗费数周——早期手工一测“好像能用”，上线后却在各种未曾明说的隐性预期上频频翻车；而一套精心设计的评估原本在第一天就能把这些问题摊在桌面上。说到底，编写评估任务本身，就是检验产品需求是否已经足够清晰、可以动工开发的最佳压力测试。

 我们强烈推崇**评估驱动开发（eval-driven development）**：在智能体还做不到某项规划能力之前，就先写好对应的评估，然后一路迭代直到智能体达标。在内部，我们经常开发一些今天“勉强够用”、实质上是在押注几个月后新一代模型能力的前瞻功能。初始通过率偏低的能力评估，能让这种押注清晰可见——每当新模型出炉，跑一遍套件，立刻就能看清哪些前瞻押注兑现了回报。

 离产品需求和终端用户最近的人，最有资格定义什么叫成功。凭借如今的模型能力，产品经理、客户成功经理乃至销售同学，完全可以直接用 Claude Code 提交一个 PR 来贡献新的评估任务——放手让他们参与进来，甚至主动为他们铺好工具通道！

## 五、将评估与其他方法结合，全面理解智能体表现（How evals fit with other methods）

 自动化评估可以在不触碰生产环境、不打扰任何真实用户的前提下，对智能体一口气跑完数千道测试任务。但它只是全面洞察智能体表现的拼图之一。完整的认知图景还需要把**生产监控、用户反馈、A/B 测试、人工执行轨迹审查以及系统化人工评测研究**有机融合起来。

| 方法与定位 | 核心优势（Pros） | 主要局限（Cons） |
| --- | --- | --- |
| **自动化评估** / Automated evals / 无需真实用户，程序化自动运行测试 | • 极大加快研发迭代节奏 / • 结果完全可复现 / • 对真实用户零影响 / • 可在每次代码提交时自动触发 / • 无需上线生产即可大规模压测各类场景 | • 前期搭建需要一定工程投入 / • 需随产品与模型演进持续维护，防止脱节漂移 / • 若脱离真实使用分布，容易制造虚假安全感 |
| **生产监控** / Production monitoring / 在线上系统实时追踪指标与报错 | • 规模化呈现真实用户的实际行为 / • 能捕获合成评估遗漏的真实长尾问题 / • 提供智能体线上实际表现的客观真值 | • 属于事后被动响应，发现时问题已触达用户 / • 线上信号往往夹杂大量噪声 / • 需要投入埋点与可观测性建设 / • 缺少可直接打分的标准答案 |
| **A/B 测试** / A/B testing / 用真实线上流量对比不同版本 | • 直接度量真实用户结果（留存率、任务完成率等） / • 有效控制外部混杂变量 / • 系统化且易于规模化运行 | • 周期漫长，需数天至数周方可达统计显著，且依赖充足流量 / • 只能验证已经部署上线的改动 / • 若不深入审阅执行轨迹，很难解释指标升降背后的深层“原因” |
| **用户反馈** / User feedback / 点踩、报错单等显式用户信号 | • 暴露团队事前根本没预料到的盲区 / • 自带来自真实用户的鲜活案例 / • 反馈内容往往与核心产品目标强相关 | • 样本稀疏且存在自选择偏差 / • 明显向极端严重故障倾斜 / • 用户很少能说清*为什么*出错 / • 无法自动化采集闭环 / • 主要靠用户帮着抓 Bug 会损害产品口碑 |
| **人工执行轨迹审查** / Manual transcript review / 由人亲眼通读智能体完整对话与调用记录 | • 快速建立对各类失效模式的直觉认知 / • 捕捉自动化检查漏掉的细腻质量瑕疵 / • 帮助团队对齐“什么是好”并摸透落地细节 | • 耗时耗力 / • 难以规模化覆盖 / • 抽样覆盖面不稳定 / • 审查疲劳或审查者差异会影响信号一致性 / • 通常只能产出定性判断，缺乏清晰量化分数 |
| **系统化人工评测研究** / Systematic human studies / 由受过训练的评测员结构化打分 | • 由多位人类评测员产出黄金标准级质量判定 / • 从容应对高度主观或含糊的复杂任务 / • 为改进模型评分器提供高质量校准信号 | • 成本相对昂贵且交付周期偏长 / • 难以高频常态化运行 / • 评测员之间出现分歧时需额外仲裁对齐 / • 法律、金融、医疗等高门槛领域必须聘请专业人类专家 |



 这六种方法分别锚定智能体研发的不同阶段：**自动化评估**在上线前和 CI/CD 流水线中最具威力，每次代码改动和模型升级都自动触发，构成拦截质量问题的第一道防线；**生产监控**在上线后接棒，用于侦测数据分布漂移与意料之外的现实故障；当你积累了足够线上流量，**A/B 测试**负责验证重大改动是否真正带来了业务收益；**用户反馈与人工轨迹审查**则是贯穿全程的日常功课——持续分拣用户反馈、每周抽样精读一批执行轨迹，发现苗头随时深挖；而**系统化人工评测研究**，则留给最关键的刀刃环节：校准 LLM 评分器，或在高度主观、必须以人类共识为基准的任务中一锤定音。

> **【图表说明】** 官方原图（中文化）：就像安全工程领域经典的[瑞士奶酪模型（Swiss Cheese Model）](https://en.wikipedia.org/wiki/Swiss_cheese_model)一样，没有任何单一评估层能够拦截所有问题。唯有将多种评估手段组合起来，从某一层漏网的故障才会被另一层牢牢接住。



 最顶尖的工程团队总是将上述手段协同并用：**用自动化评估驱动高速迭代，用生产监控锚定客观真值，用定期人工评审校准标尺。**

## 六、结语（Conclusion）

 没有评估的团队，注定被困在被动救火的泥潭里——修好一处故障又冒出另一处，分不清究竟是真实回归还是随机噪声。而尽早投入评估的团队收获的则是截然相反的正向飞轮：每一次失败都会沉淀为测试用例，测试用例筑起防止回归的高墙，客观指标彻底取代拍脑袋猜测。评估为整个团队立起一座清晰可见的攀登目标，把模糊的“智能体好像变差了”转化为精准可执行的工程行动。它的复利效应极为惊人——前提是你把它当作系统的核心支柱，而不是上线前临时应付的收尾附件。

 尽管不同类型智能体的评估模式各有侧重，但本文揭示的底层基本功始终不变：**尽早起步，别苦等所谓完美的评估集；从真实的失败案例中取材；定义无歧义、经得起推敲的成功标准；审慎设计并组合多类评分器；确保测试题对模型有足够挑战性；持续打磨评估本身以提高信噪比；以及——务必亲眼去读执行轨迹！**

 AI 智能体评估仍是一个方兴未艾、高速演进的新兴领域。随着智能体开始承担更长周期的任务、在多智能体系统中协同作战，并涉足越来越多高度主观的创造性工作，我们的评估技术也必将随之不断演进。随着实践的深入，我们也会持续分享更多前沿经验。

## 七、附录：评估框架选型参考（Appendix: Eval frameworks）

 市面上已经有多款开源和商业评估框架，能够帮助团队不必从零手写底层基础设施，快速搭建智能体评估。具体选哪一款，取决于你的智能体类型、现有技术栈，以及你究竟需要离线评估、生产可观测性，还是二者兼备。

- **[Harbor](https://harborframework.com/)**：专为在容器化环境中运行智能体而设计，提供跨云厂商大规模并发调度试次的基础设施，以及一套用于定义测试任务与评分器的标准化格式。像 Terminal-Bench 2.0 这样的热门基准正是通过 Harbor registry 发布的，让团队能极其方便地同时运行业界标准基准与自建专属评估套件。
- **[Braintrust](https://www.braintrust.dev/)**：将离线评估、生产可观测性与实验追踪融为一体的平台，非常适合既要在开发期快速迭代、又要在生产环境严密监控质量的团队。其内置的 `autoevals` 工具库预置了事实性、相关性等常见维度的开箱即用评分器。
- **[LangSmith](https://docs.langchain.com/langsmith/evaluation) 与 [Langfuse](https://langfuse.com/)**：LangSmith 提供完整的链路追踪、离线/在线评估与数据集管理能力，并与 LangChain 生态深度集成；而 Langfuse 提供了类似的完整功能，作为可自托管的开源替代方案，尤其适合对数据本地驻留有严格合规要求的团队。
- **[Arize](https://arize.com/)**：旗下既有开源平台 **Phoenix**（支持 LLM 追踪、调试以及离线/在线评估），也提供商业化 SaaS 产品 **AX**，在 Phoenix 基础上进一步扩展了大规模评估、持续优化与线上监控能力。


 当然，许多团队也会组合使用多款工具、自研轻量级评估框架，甚至直接从几段简单的评估脚本起步。我们的经验是：框架虽然能有效提速并推动标准化，但**再好的框架，其上限也取决于跑在里面的测试任务质量。**最务实的策略往往是迅速选定一个贴合当前工作流的框架，然后把绝大部分精力投入到评估内容本身——持续打磨高质量的测试用例与精准的评分器。

## 💡 译者附注（非原文）：如何把本篇 Eval 体系落地到 AI 客服与全自动运营 Agent



如果你正在搭建或维护生产级的 AI 客服或全自动运营智能体，可以直接按以下 4 个最小动作把本文方法跑起来，不必等“大而全”的平台：

1. **3 天攒齐 50 条“真实工单”种子题集（且正反双测）**：直接从最近两周的差评工单、升级工单和高频运营操作里抽 50 条真实案例——其中至少留出 30% 的“负例”（如超额退款应拒绝、信息不全应先核验或转人工），防止把智能体调成“逢求必应的滥好人”。
1. **用 `Outcome` 状态核验替代“只看回复话术”**：客服嘴上说“已为您办理退款/已发放补偿券”毫无意义。代码评分器必须直连测试环境数据库或沙箱接口，核验退款表状态、发券流水、工单关闭状态与金额上限（如 `amount <= 100`）；语气共情、政策依据引用和清晰度，再交给拆好维度的独立 LLM 裁判打分。
1. **用 `pass^k` 为全自动高危权限立生死门**：给人工坐席生成回复草稿或运营文案，只需衡量 `pass@1` / `pass@3`；但凡涉及**全自动发券、自动打款退款、修改线上活动配置或批量触达用户**，上线前必须在沙箱里用 `pass^5`（甚至 `pass^10`）卡死稳定性红线——单次 85% 成功率看似很高，连跑 5 次全过的概率却只有 44%，绝不能贸然放开全自动权限。
1. **固化“每周精读 20 条失败轨迹 + 故障一键转回归题”的习惯**：在群里发周报分数前，负责人必须亲手翻完至少 20 条失败 `Transcript`，先剔除评分器误杀和沙箱环境脏数据；凡是线上复现过的真实故障，修复当天就补进 CI 回归套件，让每一次线上踩坑都变成永久护城河。
