# AI 智能体的高效上下文工程

Effective context engineering for AI agents

>   **发布日期：**2025 年 9 月 29 日 **团队：**Anthropic Engineering **作者：**Anthropic Applied AI Team **预计阅读：**约 13 分钟  [查看官方英文原文 ↗](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

 在应用 AI 领域聚焦了数年“提示词工程（prompt engineering）”之后，一个新概念开始成为舞台中心：**上下文工程（context engineering）**。基于大语言模型做开发，重心正越来越从“绞尽脑汁推敲单条提示词的措辞”转向一个更宏大的问题：“**什么样的上下文配置，最有可能引导模型产出我们期望的行为？**”

 所谓**上下文（Context）**，是指向大语言模型采样生成时传入的全部 Token 集合。摆在工程师面前的核心问题，是在 LLM 固有约束下最大化这组 Token 的效用，从而持续稳定地达成预期目标。要高效驾驭 LLM，往往需要“从上下文视角出发来思考（thinking in context）”——也就是说，要通盘审视任意时刻呈现在 LLM 眼前的完整状态，以及这种状态可能触发哪些行为。

 在本文中，我们将探讨上下文工程这门新兴技艺，并为你构建可控、高效的智能体提供一套精炼的心智模型。

## 一、上下文工程 vs. 提示词工程（Context engineering vs. prompt engineering）

 在 Anthropic，我们把上下文工程视为提示词工程的自然演进。**提示词工程**关注如何编写与组织 LLM 指令以获得最优输出（概述与实用提示词工程策略可参阅[我们的官方文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)）；而**上下文工程**则是指在 LLM 推理全过程中，用于精选并持续维护最优 Token（信息）集合的整套工程策略——这涵盖了系统提示词之外、可能进入上下文窗口的所有其他信息。

 在 LLM 工程的早期，编写提示词占据了绝大部分工作量，因为日常聊天之外的大多数用例都需要为一次性分类或文本生成任务打磨单轮提示词。顾名思义，提示词工程的核心焦点是如何写好提示词（尤其是系统提示词）。然而，随着我们转向构建能够在多轮推理和更长周期内自主运行的强力智能体，我们必须具备管理**整体上下文状态**的策略——包括系统指令、工具定义、[模型上下文协议（MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)、外部数据、历史消息记录等。

 在循环中运行的智能体会不断产生越来越多可能对下一轮推理有用的数据，这些信息必须被周期性地提纯精炼。**上下文工程，正是从这个不断演变的候选信息池中，精选出该放进有限上下文窗口的内容的[艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)。**

> **【图表说明】** 官方原图（中文化）：与一次性撰写提示词的离散任务不同，上下文工程是持续迭代的——每次决定把什么内容传给模型时，上下文精选（curation）阶段都在发生。



## 二、为什么上下文工程对构建强力智能体至关重要？（Why context engineering is important）

 尽管大语言模型速度飞快、且能吞吐越来越庞大的数据量，但我们观察到，LLM 和人类一样，超过一定阈值后也会注意力涣散或陷入混乱。“大海捞针（needle-in-a-haystack）”类基准研究揭示了一个重要现象——**[上下文腐败（context rot）](https://research.trychroma.com/context-rot)**：**随着上下文窗口中 Token 数量不断增加，模型从上下文中准确召回信息的能力会持续下降。**

 不同模型的衰减坡度或许有缓有急，但这一特性存在于**所有**模型之中。因此，上下文必须被当作一种**边际收益递减的有限资源**来对待。正如人类[工作记忆容量有限](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)，LLM 在解析海量上下文时也在消耗自己的**“注意力预算（attention budget）”**。每多塞进一个新 Token，都会消耗一部分预算，因此我们越发需要精心挑选呈现在模型面前的每一份信息。

 这种注意力稀缺源于 LLM 的底层架构约束。大语言模型基于 [Transformer 架构](https://arxiv.org/abs/1706.03762)，允许上下文中的每个 Token [关注到其他所有 Token](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)——对于 `n` 个 Token，这意味着高达 **`n²` 组两两注意力关系**。随着上下文拉长，模型捕捉这些两两关系的能力被不断摊薄，在“上下文长度”与“注意力聚焦”之间形成了天然张力。此外，模型在训练数据分布中接触到的短序列远多于超长序列，导致模型处理跨长距离依赖的训练经验更少、为此分配的专用参数也更有限。

 [位置编码插值](https://arxiv.org/pdf/2306.15595)等技术虽然能让模型把原本针对较短上下文训练的能力适配到更长序列，但仍会带来一定程度的位置感知精度损耗。这些因素叠加在一起，带来的并非断崖式下跌，而是一条**平缓的性能衰减曲线**：模型在长上下文中依然很强，但相比短上下文，其在精准信息检索和长程推理上的敏锐度会有所下降。正是这些客观现实，决定了深思熟虑的上下文工程是打造高能智能体的必经之路。

## 三、高效上下文的解剖学（The anatomy of effective context）

 既然 LLM 受制于有限的注意力预算，优秀的上下文工程核心就一句话：**寻找规模最小的高信噪比 Token 集合，以最大化达成期望结果的概率。**说起来容易做起来难，下面我们将这条指导原则拆解到上下文的各个核心组成部分中。

### 1. 系统提示词：找到“恰当的高度（Right Altitude）”

 系统提示词应当极其清晰、用词简洁直白，并将思想表达在适合智能体的**“恰当高度”**上。所谓恰当高度，就是介于两种常见失败极端之间的“恰到好处”的平衡区（Goldilocks zone）：

- **一个极端（过低、过死）**：工程师为了逼出精确行为，在提示词里硬编码了极其复杂脆弱的 `if-else` 逻辑。这会让系统极其脆弱，后期维护成本飙升。
- **另一个极端（过高、过虚）**：工程师只给出含糊笼统的高层指导，既没给 LLM 传递关于期望输出的具体信号，又错误地假设模型天然共享你的隐含背景。


 最优的高度在于平衡：**具体到足以有效引导行为，同时又灵活到足以给模型提供强有力的启发式原则来指导行为。**

> **【图表说明】** 官方原图（中文化）：校准系统提示词——光谱的一端是脆弱的 `if-else` 硬编码提示词，另一端则是过于宽泛或错误假设共享上下文的提示词。



 我们建议将提示词划分为清晰的区块（例如 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 等），并使用 XML 标签或 Markdown 标题等技术界定边界（尽管随着模型能力越来越强，提示词的精确排版格式本身正变得不那么重要）。

 无论你决定如何组织系统提示词，都应追求能够完整勾勒预期行为的**最小信息集**（注意：“最小”并不一定意味着“越短越好”，你依然要提前给足必要信息以确保智能体遵循期望行为）。最佳实践是：**先用当前最强的模型配合极简提示词跑测试，观察其在任务上的表现，再针对初测中暴露出的具体失败模式，逐步补入清晰指令与示例以提升效果。**

### 2. 工具定义：拒绝臃肿与功能重叠

 工具让智能体得以操作外部环境，并在工作过程中不断拉入新的上下文。由于工具定义了智能体与其信息/行动空间之间的契约，工具必须极力促进效率——既要返回节省 Token 的精炼信息，又要引导高效的智能体行为。

 正如我们在[《与智能体协作编写高效工具》](https://www.anthropic.com/engineering/writing-tools-for-agents)（本辑第 02 篇）中所探讨的，工具应当易于 LLM 理解、功能重叠极少；就像优秀代码库里的函数一样，工具应做到自包含、容错稳健、用途一目了然，输入参数语义清晰无歧义且顺应模型长处。

 我们见过的最常见失败模式之一，就是**臃肿的工具集（bloated tool sets）**——功能包罗万象，却导致模型在“到底该选哪个工具”上陷入模棱两可。**如果连人类工程师都无法果断指出某个场景下该用哪个工具，就绝不能指望 AI 智能体做得更好。**正如后文将讨论的，为智能体精简出最小可行工具集，也能让长对话过程中的上下文维护与裁剪可靠得多。

### 3. 少样本示例（Few-shot Examples）：胜过千言万语的“图画”

 提供示例（即少样本提示 / few-shot prompting）依然是我们强烈推荐的最佳实践。但不少团队习惯把一整张冗长的边缘情况清单塞进提示词，企图穷举 LLM 应该遵守的每一条细则——我们并不推荐这样做。相反，建议精选一组**多样化、具代表性的典型范例（canonical examples）**，精准勾勒出智能体的期望行为。对 LLM 而言，好的示例就是“一图胜千言”。

 总之，对于上下文的每一个组件（系统提示词、工具、示例、历史消息等），总原则都是：深思熟虑，保持信息充实而又高度紧凑。接下来，我们看看如何在运行时动态获取上下文。

## 四、上下文检索与智能体自主搜索（Context retrieval and agentic search）

 在[《构建高效的智能体》](https://www.anthropic.com/research/building-effective-agents)（本辑第 01 篇）中，我们区分了基于 LLM 的工作流与智能体。自那以后，我们逐渐收敛到一个[极简定义](https://simonwillison.net/2025/Sep/18/agents/)：**智能体 = 在循环中自主使用工具的 LLM。**

 在与客户的共同实践中，我们看到整个行业正收敛到这一简洁范式上。随着底层模型越来越强，智能体的自主级别也能水涨船高：更聪明的模型能够在错综复杂的问题空间里自主摸索路径，并自行从报错中恢复。

 这也带来了工程师设计上下文方式的深刻转向。目前许多 AI 原生应用在推理前，会先靠向量嵌入（embedding）做预检索来召回相关上下文；但随着行业向更智能体化的方向演进，越来越多团队正结合**“即时（just in time）”上下文策略**来增强检索系统。

 所谓“即时”策略，是指不再提前预处理并塞入所有可能相关的数据，而是让智能体只在上下文中保留**轻量级引用标识**（文件路径、已保存的查询、网页链接等），在运行时按需调用工具动态加载数据。Anthropic 的编程智能体 [Claude Code](https://www.anthropic.com/claude-code) 正是用这种方式处理大型数据库分析：模型可以编写精准查询、把结果落盘，并借助 `head`、`tail` 等 Bash 命令分析海量数据，**自始至终都不必把庞大的完整数据对象塞进上下文窗口**。这与人类认知如出一辙——我们通常不会把整座语料库背进脑子，而是借助文件系统、收件箱和书签等外部组织与索引体系按需取用。

 除了存储效率之外，这些引用的**元数据**本身也是精细引导行为的极佳机制（无论显式提供还是直观呈现）。对在文件系统中工作的智能体而言，`tests` 目录下的 `test_utils.py` 与 `src/core_logic/` 目录下的同名文件显然意味着截然不同的用途；文件夹层级、命名规范与时间戳都提供了关键信号，帮助人类和智能体理解“何时以及如何使用这些信息”。

 让智能体自主探索和检索数据，还实现了**渐进式披露（progressive disclosure）**——即让智能体通过层层探索逐步发现相关上下文。每一步交互产出的线索都会指导下一步决策：文件大小暗示复杂度，命名规范提示职责，时间戳可作为相关性的代理指标。智能体得以逐层拼装认知，工作记忆里始终只保留当下真正需要的内容，并借助笔记策略获得额外的持久化能力。这种自我管理的上下文窗口让智能体始终聚焦于相关子集，而不会被详尽却可能无关的噪音淹没。

 当然，这也有权衡代价：运行时动态探索比读取预计算数据更慢，且需要审慎而有明确取舍的工程设计，确保 LLM 手握恰当的工具与启发式原则来高效导航信息空间——缺乏引导的智能体可能会误用工具、钻进死胡同或漏掉关键信息。

 在某些场景下，最高效的智能体会采用**混合策略（hybrid strategy）**：为了速度预先加载部分核心数据，同时保留按需自主探索的能力。“恰当”自主程度的决策边界取决于具体任务。Claude Code 正是采用这种混合模式的典型代表：启动时直接把 [`CLAUDE.md`](http://claude.md) 文件原样加载进上下文，同时提供 `glob` 和 `grep` 等基础原语让它即时探索环境并按需检索文件，巧妙绕开了索引过时和复杂语法树维护的难题。

 对于内容动态变化较少的场景（如法律或金融工作），混合策略尤为合适。随着模型持续变强，智能体设计将越来越趋向于“让聪明的模型自主聪明行事”，逐步减少人工编排干预。鉴于该领域日新月异的发展速度，**“做能跑通的最简单方案（do the simplest thing that works）”**大概率仍将是我们给基于 Claude 构建智能体的团队的最佳忠告。

## 五、面向长周期任务的上下文工程（Context engineering for long-horizon tasks）

 长周期任务要求智能体在总 Token 数远超窗口上限的连续操作序列中，依然不丢上下文、不偏离目标、保持思路连贯。面对持续数十分钟甚至数小时的任务（如大型代码库迁移或综合深度研究），智能体需要专门的工程手法来突破上下文窗口的局限。

 坐等更大的上下文窗口听起来像是一条捷径。但在可预见的未来，只要追求顶尖的智能体表现，**任何尺寸的上下文窗口都仍将面临上下文污染与信息相关性稀释的挑战。**为让智能体在超长周期中稳健工作，我们总结了三种直击上下文污染与膨胀的核心技术：**上下文压缩（compaction）、结构化笔记（structured note-taking）以及多智能体/子智能体架构（multi-agent / sub-agent architectures）**。

### 1. 上下文压缩（Compaction）

 上下文压缩是指在对话逼近上下文窗口上限时，总结提炼已有内容，并用这份摘要开启一个全新的上下文窗口继续工作。它通常是维持长程连贯性的第一根杠杆，核心在于高保真地提炼历史上下文，让智能体几乎不掉状态地无缝接续任务。

 例如在 Claude Code 中，我们把消息历史交给模型来总结并压缩最关键的细节——保留架构决策、未解决的 Bug 和关键实现细节，同时丢弃冗余的工具输出与过程对话；随后智能体带着这份压缩摘要以及最近访问的 5 个文件继续干活，让用户无需操心窗口上限。

 压缩的艺术在于**“留什么、丢什么”的取舍**——过度激进的压缩可能误删某些当下不起眼、但后续才凸显价值的细微线索。对于实现压缩系统的工程师，我们建议拿着真实的复杂智能体轨迹反复调优压缩提示词：**先最大化召回率（recall）**，确保不漏掉任何关键信息，**再逐步迭代提升精确率（precision）**，剔除冗余废话。

 一个极容易入手的冗余清理点是**清除历史工具调用与结果（tool result clearing）**——一条工具在几十轮前调用完之后，智能体为何还需要反复盯着那一大段原始返回结果？这是最安全、侵入性最轻的压缩手段之一，近期已作为一项功能正式上线 [Claude 开发者平台](https://www.anthropic.com/news/context-management)。

### 2. 结构化笔记（Structured note-taking）

 结构化笔记（又称智能体记忆 / agentic memory），是指智能体在运行中定期把关键结论和进度持久化写入**上下文窗口之外**的外部存储，并在需要时重新拉回窗口。这种模式开销极低却能提供持久记忆——就像 Claude Code 维护待办清单，或自定义智能体维护一份 `NOTES.md` 文件，让智能体跨越数十次工具调用依然牢记任务进度与关键依赖。

 [Claude 玩《宝可梦》](https://www.twitch.tv/claudeplayspokemon)的实验生动展示了记忆在非编程领域的变革力：智能体在数千步游戏进程中维护精确记录（如“过去 1,234 步我一直在 1 号道路练级，皮卡丘已升了 8 级，目标是 10 级”）；无需任何关于记忆结构的提示词指导，它自己画出了探索地图、记下解锁的关键成就，并整理出针对不同对手的战斗策略笔记，帮助自己学习哪些招式对不同对手最有效。上下文重置后，它读一遍自己的笔记便能无缝接续数小时的练级或迷宫探索——单靠把全部信息塞在 LLM 上下文窗口里，根本无法实现这种跨周期策略连贯性。

 作为 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude 开发者平台上以公开测试（public beta）形式推出了一款[记忆工具（memory tool）](http://anthropic.com/news/context-management)，使智能体能够通过基于文件的系统更轻松地在上下文窗口之外存储和查阅信息。这使得智能体能够随时间积累知识库、跨会话保持项目状态，并在无需将全部内容留在上下文中的情况下引用过往工作。

### 3. 子智能体架构（Sub-agent architectures）

 子智能体架构提供了突破上下文限制的第三条路径：不再指望单个智能体独自扛起整个项目的全量状态，而是让**专职子智能体在各自干净的上下文窗口中处理聚焦子任务**。主控智能体负责高层规划与协调，子智能体负责深入技术细节或调用工具搜寻证据。每个子智能体内部可能深度探索、消耗数万甚至更多 Token，但最终**只向主控智能体交回一份高度浓缩的摘要（通常仅 1,000–2,000 tokens）**。

 这种做法实现了彻底的关注点分离——繁杂的搜索过程与脏上下文被严密隔离在子智能体内，主控智能体得以专注综合研判。正如我们在[《我们如何构建多智能体研究系统》](https://www.anthropic.com/engineering/multi-agent-research-system)（可对应参考本辑第 09 篇）中所探讨的，在复杂研究任务上，这一架构相对单智能体带来了大幅提升。

**三种长程策略如何选择？取决于任务特性：**

- **上下文压缩（Compaction）**：适合需要大量来回交互、保持连续对话流的任务；
- **结构化笔记（Note-taking）**：适合里程碑清晰、逐步演进的迭代开发任务；
- **多智能体/子智能体架构（Multi-agent / Sub-agent architectures）**：适合并行探索能带来显著收益的复杂调研与分析任务。


即便模型不断进步，在漫长交互中维持连贯性仍将是打造更强智能体的核心命题。

## 六、结语（Conclusion）

 上下文工程标志着我们基于 LLM 构建应用方式的根本转变。随着模型能力越来越强，挑战已不只是写出完美的单条提示词，而是**在每一步推理中，审慎精选究竟让什么信息进入模型有限的注意力预算**。无论是为长程任务做上下文压缩、设计高 Token 效率的工具，还是让智能体即时探索环境，核心指导原则始终如一：**找到规模最小的高信噪比 Token 集合，最大化达成预期结果的概率。**

 本文介绍的具体手法必将随模型演进继续迭代——我们已经看到，更聪明的模型需要的死板人工编排越来越少，自主度越来越高。但无论能力如何扩张，把上下文视为珍贵且有限的资源来对待，永远是构建可靠、高效智能体的立身之本。

 即日起，你就可以在 Claude 开发者平台上手实践上下文工程，并通过我们的 [记忆与上下文管理 Cookbook](https://platform.claude.com/cookbook/tool-use-memory-cookbook) 获取实用技巧与最佳实践。

- **把客服系统提示词控制在“恰当高度”**：不要把 500 条售后细则全塞进 GPT-6.2 的 System Prompt，只保留角色边界、红线原则和 3–5 个典型范例；把细则拆成知识库文档目录，通过业务 MCP 让智能体按工单类型即时（just-in-time）检索加载。
- **超长扯皮工单自动启用“旧工具结果清理 + 结构化摘要”**：当一个复杂售后单超过 15 轮对话，先清掉 5 轮前的原始物流/订单 JSON 返回，只把已核实事实（订单号、破损凭证、已承诺方案）压缩写入工单 `case_notes`，防止上下文腐败导致模型忘记先前承诺。
- **用只读子智能体隔离全自动运营的“脏巡检”**：每日自动巡检退款率异常、大促库存告警或差评归因时，由主控编排器派发只读子智能体去翻查数万行日志与工单，子体只回传 ≤ 1,500 字的根因摘要和证据链接，让主控在干净窗口里做经营决策。
- **Codex 开发期就同步对齐这套架构**：让 Codex 维持 ≤ 100 行的 `AGENTS.md` 与 `docs/` 业务规则抽屉，这本身就是“混合上下文策略”在代码工程中的最佳落地示范。
