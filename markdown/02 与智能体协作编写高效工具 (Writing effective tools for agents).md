# 与智能体协作编写高效工具

Writing effective tools for agents — with agents

>   **发布日期：**2025 年 9 月 11 日 **团队：**Anthropic Engineering **作者：**Ken Aizawa 等 **预计阅读：**约 15 分钟  [查看官方英文原文 ↗](https://www.anthropic.com/research/writing-tools-for-agents)

 [模型上下文协议（Model Context Protocol，简称 MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)能够为 LLM 智能体赋予潜在成百上千个工具，以解决现实世界中的各类任务。但我们该如何让这些工具发挥出最大效能？

 在本文中，我们将介绍一套无需改动底层模型训练本身、即可在多种智能体 AI 系统中显著提升表现的有效工程方法。我们首先阐述如何：

- 构建并在本地测试你的工具原型；
- 与智能体一起创建并运行覆盖全面的工具评估（evaluations）；
- 与 Claude Code 这类智能体协作，自动提升工具表现。


随后，我们总结了在这一过程中提炼出的高质量工具编写原则：

- 选择应该实现（以及**不应该**实现）的合适工具；
- 通过命名空间（namespacing）划清工具间的功能边界；
- 让工具向智能体返回有意义的高信噪比上下文；
- 优化工具返回的 Token 效率；
- 对工具描述与规格说明做提示词工程优化。

## 一、什么是“工具”？（What is a tool?）

 在计算机科学中，**确定性系统（deterministic systems）**在给定相同输入时每次都会产出相同输出；而**非确定性系统（non-deterministic systems）**——例如智能体——即便起点完全一致，也可能生成截然不同的响应。

 传统软件开发本质上是在确定性系统之间建立契约。例如调用 `getWeather("NYC")` 时，它每次都会以完全相同的方式去查询纽约的天气。

 而**工具是一种新型软件，它体现的是“确定性系统”与“非确定性智能体”之间的契约。**当用户问“我今天需要带伞吗？”，智能体可能会调用天气工具，可能凭常识直接回答，甚至可能先反问用户所在城市；偶尔，它还可能产生幻觉，甚至根本没搞明白该怎么调用某个工具。

 这意味着我们必须从根本上重构为智能体写软件的思维方式：**不要照着给人类开发者或其他后端服务写函数和 API 的老办法去写工具和 [MCP 服务器](https://modelcontextprotocol.io/)，而要专门面向智能体来设计它们。**

 我们的目标是拓宽智能体能够有效驾驭的任务版图，让它借助工具灵活走出多条通往成功的路径。令人欣慰的是，根据我们的经验，那些对智能体而言最顺手（ergonomic）的工具，对人类来说往往也同样直白好懂。

## 二、如何编写并打磨工具（How to write tools）

 本节介绍如何与智能体并肩协作，共同编写和持续改进你提供给它们的工具：先快速搭起原型并在本地实测，接着跑一遍全面的评估以量化每次改动的效果，然后与智能体协同反复迭代评估和优化，直到智能体在真实业务任务上取得稳健表现。

### 1. 搭建原型（Building a prototype）

 不亲自上手试用，很难凭空预判哪些工具对智能体来说顺手、哪些别扭。先快速搭一个工具原型。如果你借助 [Claude Code](https://www.anthropic.com/claude-code) 来编写工具（甚至一次性生成），把工具所依赖的软件库、API 或 SDK（包括 [MCP SDK](https://modelcontextprotocol.io/docs/sdk)）的官方文档喂给它大有裨益——适合 LLM 直接阅读的文档通常可以在官方文档站点的扁平文件 `llms.txt` 中找到（例如这是我们 [API 的 `llms.txt`](https://docs.anthropic.com/llms.txt)）。

 将工具封装为[本地 MCP 服务器](https://modelcontextprotocol.io/docs/develop/connect-local-servers)或[桌面扩展（DXT）](https://www.anthropic.com/engineering/desktop-extensions)，就能直接在 Claude Code 或 Claude Desktop 应用中连接实测：

- 在 Claude Code 中连接本地 MCP 服务器：运行 `claude mcp add <name> <command> [args...]`；
- 在 Claude Desktop 应用中连接本地 MCP 服务器或 DXT：分别前往 `Settings > Developer` 或 `Settings > Extensions`；
- 也可以直接把工具传入 [Anthropic API](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview) 调用中进行程序化测试。


 自己亲手试用这些工具以找出粗糙之处，并收集真实用户反馈，逐步建立起对目标使用场景与常见用户提示词的直觉。

### 2. 运行评估（Running an evaluation）

 接下来，你需要通过运行评估来客观衡量 Claude 使用这些工具的表现。从生成大量扎根于真实业务场景的评估任务开始，我们建议直接与智能体协作分析评估结果，并确定如何改进你的工具。你可以在我们的 [工具评估 Cookbook](https://platform.claude.com/cookbook/tool-evaluation-tool-evaluation) 中查看这一端到端流程。

#### 2.1 生成评估任务（Generating evaluation tasks）

有了早期原型后，Claude Code 可以快速探索你的工具并生成数十组“提示词—预期结果”测试对。提示词必须源自真实世界的使用场景，并建立在逼真的数据源与服务之上（例如内部知识库和微服务）。尽量避开过于简陋或流于表面的“假沙箱”环境，否则无法对工具形成足够的压力测试。**高质量的评估任务往往需要连续调用多个工具——有时多达数十次。**   ✓ 强评估任务示例（贴近真实复杂场景）

• “下周帮我和 Jane 约个会，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的纪要，并预订一间会议室。”

• “客户 ID 9182 反馈单次购买被扣款三次。查出所有相关日志记录，并判断是否有其他客户受同一故障影响。”

• “客户 Sarah Chen 刚提交了取消订阅申请。请准备一份挽留方案，查明：(1) 她离开的原因；(2) 什么挽留优惠最具吸引力；(3) 发出方案前需要注意哪些风险因素。”   ✗ 弱评估任务示例（过于死板简单）

• “下周帮我和 jane@acme.corp 约个会。”

• “在支付日志里搜索 `purchase_complete` 和 `customer_id=9182`。”

• “按客户 ID 45892 查找取消申请。”

 每条评估提示词都应配有一个可验证的回答或状态结果。验证器既可以简单到将模型输出与客观真值（ground truth）做精确字符串比对，也可以进阶到请 Claude 担任裁判打分。注意避免过于苛刻的验证器，以免因为格式、标点或完全合理的等价措辞差异而误判正确结果。

 针对每个测试对，你也可以选择性地标出预期应调用的工具，以衡量智能体在评估中是否真正理解了每个工具的用途。但由于解决同一个任务往往存在多条合理路径，请避免把执行策略规定得过死或过度拟合单一路径。

#### 2.2 执行评估（Running the evaluation）

我们建议直接通过 LLM API 以程序化方式跑评估：使用最简单的智能体循环（一个交替执行 LLM API 调用与工具调用的 `while` 循环），每个评估任务对应一个独立循环，只向该评估智能体提供单条任务提示词和你的工具集。

 在评估智能体的系统提示词中，建议要求它不仅输出用于验证的结构化结果块，还要输出**推理过程与反馈块**。在工具调用和最终回答之前引导模型输出这些思考，能够触发思维链（CoT）行为，提升模型的有效智能水平。如果你使用 Claude 跑评估，也可以直接开箱启用[交错思考（interleaved thinking）](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)获得类似效果。这能帮你清晰洞察智能体为什么调用或跳过某个工具，精准暴露出工具描述与规格中的薄弱环节。

 除了顶层准确率外，建议同时采集**单次工具调用与整项任务的总耗时、工具调用总次数、总 Token 消耗量、以及工具报错率**等指标。追踪工具调用轨迹能帮你发现智能体高频重复走的固定链路，从而发掘将多个零散工具合并的机会。

#### 2.3 分析结果（Analyzing results）

 智能体是帮你抓毛病的好搭档——无论是自相矛盾的工具描述、低效的工具实现还是令人困惑的参数 Schema，它们都能给出反馈。但切记：**智能体在反馈中“没说出来的东西”，往往比说出来的更重要。**LLM 并不总是[言行一致](https://www.anthropic.com/research/tracing-thoughts-language-model)。

 仔细观察智能体在哪里卡壳或迷糊：通读评估智能体的推理与反馈（CoT）来发现卡点，更要**直接查看原始完整记录（raw transcripts，包含每一次工具调用和工具返回）**，揪出那些没写在 CoT 里的隐蔽行为。读出言外之意——记住，评估智能体自己并不一定知道什么是正确答案和最优策略。

 分析你的工具调用指标：如果出现大量重复冗余的工具调用，往往说明该重新校准分页大小或 Token 上限参数；如果频繁出现“无效参数”报错，则说明工具需要更清晰的描述或更好的调用示例。例如，当我们推出 Claude 的[网页搜索工具](https://www.anthropic.com/news/web-search)时，曾通过分析发现 Claude 会毫无必要地在 `query` 参数后面擅自拼上 `2025`，导致搜索结果产生偏差、效果下降——最终我们通过改进工具描述把 Claude 引导回了正轨。

### 3. 与智能体协同优化（Collaborating with agents）

 你甚至可以直接让智能体来分析评估结果并帮你改写工具。只需把评估智能体的运行记录拼接起来粘贴给 Claude Code——Claude 非常擅长分析长记录并一次性重构大批工具，确保工具实现与描述在改动后依然保持自洽。

 事实上，本文中的绝大多数经验，正是源于我们反复借助 Claude Code 优化自身内部工具的实战过程。我们的评估直接构建在内部真实工作空间之上，完整映射了真实项目、文档与消息的复杂度。我们还保留了**留出测试集（held-out test sets）**，防止工具在“训练用”评估集上过拟合。结果证明，即便面对原本由我们研究员手写或由 Claude 生成的“专家级”工具实现，经过这种闭环协作优化，依然能在留出测试集上榨取出显著的额外性能提升。

## 三、编写高效工具的核心原则（Principles for writing effective tools）

本节将上述实战经验提炼为五条编写高效工具的核心指导原则。

### 原则 1：为智能体选择恰当的工具（Choosing the right tools for agents）

 **工具越多，并不一定效果越好。**我们观察到的一个常见误区，是不管是否适合智能体，直接把现有软件功能或后端 API 端点原封不动地一层套壳包成工具。之所以行不通，是因为智能体与传统软件拥有截然不同的“可供性（affordances）”——也就是说，它们感知可借助工具执行哪些潜在动作的方式截然不同。

 LLM 智能体的“上下文”是有限的（即单次能处理的信息量存在上限），而传统计算机内存却廉价且充裕。以在通讯录里查找联系人为例子：传统软件程序可以高效地存储联系人列表并逐条检查后再移向下一条；但如果一个 LLM 智能体调用了返回**所有联系人**的工具，再被迫逐 Token 从头读到尾，就会把有限的上下文空间白白浪费在无关信息上（就像在纸质通讯录里从第一页逐行翻到底做暴力穷举搜索）。对智能体和人类都更自然高效的做法，是先直接跳到相关页（例如按字母顺序查找）。

 我们建议从**少量精心设计、直击高价值工作流的工具**起步，与你的评估任务精准对齐，再逐步扩展。例如在通讯录场景中，应当优先实现 `search_contacts` 或 `message_contact`，而不是 `list_contacts`。

 工具可以在底层合并多项零散操作（或多次 API 调用），为返回结果补充关联元数据，或者把高频串联的多步操作收口成一次工具调用：

- 与其拆成 `list_users`、`list_events` 和 `create_event` 三个工具，不如合并为一个 `schedule_event` 工具，在内部查完空闲时间并直接完成日程预订；
- 与其提供 `read_logs` 一股脑读全量日志，不如提供 `search_logs`，只返回命中的关键日志行及其上下文片段；
- 与其拆成 `get_customer_by_id`、`list_transactions` 和 `list_notes`，不如提供一个 `get_customer_context` 工具，一次性把该客户近期最相关的全貌信息整理返回。


 确保你构建的每一个工具都有清晰、独特的用途。工具应当让智能体能够像人类拿到同样底层资源时那样拆解并解决问题，同时大幅减少中间结果对上下文的消耗。工具过多或功能重叠会分散注意力、干扰智能体选择高效路径，审慎克制地规划“做哪些工具、不做哪些工具”会带来极高回报。

### 原则 2：为工具划分命名空间（Namespacing your tools）

 你的 AI 智能体未来可能会同时接入数十个 MCP 服务器和成百上千个不同工具（包括其他开发者编写的）。一旦工具功能重叠或用途含糊，智能体就会在选用时犯迷糊。

 **命名空间（使用共同前缀将相关工具归类）**能在海量工具之间划出清晰界线（许多 MCP 客户端默认也会这么做）。例如按服务划分（`asana_search`、`jira_search`）以及按资源划分（`asana_projects_search`、`asana_users_search`），能显著帮助智能体在正确时机选对工具。

 我们还发现，采用前缀式还是后缀式命名空间，对工具调用评估得分有着不可忽视的影响，且不同 LLM 表现各异，建议结合你自己的评估结果来选定命名规范。

 智能体可能会调错工具、用错参数调用正确工具、调用工具次数不足，或者错误地解析工具返回结果。通过有选择地实现名称契合自然任务分工的工具，你既减少了塞进上下文的工具定义数量，又把一部分本该消耗智能体上下文去硬算的逻辑下沉到了确定性的工具调用内部，从而降低智能体整体的出错风险。

### 原则 3：让工具返回有意义的上下文（Returning meaningful context from your tools）

 同理，工具实现应当谨慎克制，**只向智能体返回高信噪比信息**：优先保证上下文相关性，而不是一味追求全字段灵活性，尽量剔除底层技术标识符（如 `uuid`、`256px_image_url`、`mime_type`）。像 `name`、`image_url`、`file_type` 这类直观字段，更能直接支撑智能体的下游判断与回复。

 智能体处理自然语言名称、术语或语义化标识的能力，也远远强于处理晦涩难懂的随机串。我们发现，仅仅是将杂乱的字母数字 UUID 映射为更具语义可读性的名称（甚至是从 0 开始的简短索引 ID），就能大幅减少幻觉、显著提高 Claude 在检索任务上的准确率。

 在某些场景下，智能体确实需要兼顾自然语言展示和技术 ID（例如为了驱动后续工具调用：`search_user(name='jane') → send_message(id=12345)`）。你可以通过在工具中暴露一个简单的 `response_format` 枚举参数来兼得二者，让智能体自主选择返回“精简（`concise`）”还是“详细（`detailed`）”格式（见下图）。你还可以像 GraphQL 那样扩展更多档位，精确选择需要接收哪些信息。下面是一个用于控制工具响应详略程度的 `ResponseFormat` 枚举示例：

```typescript
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```



 下面对比同一条 Slack 检索工具（`slack - search (MCP)`）在 `detailed`（**206 tokens**，返回完整频道 ID、用户 ID、时间戳 `TS` 与附件名）与 `concise`（**72 tokens**，仅保留紧凑的频道、发信人、正文与日期列表）两种模式下的真实返回效果：

> **【图表说明】** 官方原图：`detailed` 模式工具响应示例（**206 tokens**）——包含 `channel_id`、`user_id`、`TS` 等元数据，供后续链式调用使用。



> **【图表说明】** 官方原图：`concise` 模式工具响应示例（**72 tokens**）——仅保留核心讨论正文，省略各类底层 ID，Token 消耗降至约 1/3。

   **官方图注：**Slack 话题及其回复通过唯一的 `thread_ts` 标识，拉取话题回复时必须用到该字段。`thread_ts` 以及其他 ID（`channel_id`、`user_id`）可以从 `"detailed"` 工具响应中获取，以便继续发起需要这些 ID 的下游工具调用；`"concise"` 工具响应则只返回话题内容并排除 ID。在此示例中，使用 `"concise"` 工具响应仅消耗约三分之一的 Token。

 甚至工具返回的数据格式（例如 XML、JSON 或 Markdown）本身也会影响评估表现，没有放之四海而皆准的唯一答案。这是因为 LLM 基于下一 Token 预测训练，往往在贴合其训练语料分布的格式上表现更好。最佳响应结构会因任务与智能体的不同而存在很大差异，我们建议根据你自己的评估实测来选定最佳返回结构。

### 原则 4：优化工具返回的 Token 效率（Optimizing tool responses for token efficiency）

 优化返回上下文的“质量”很重要，控制返回给智能体的上下文“数量”同样关键。对于任何可能吐出海量内容的工具，我们建议组合使用**分页（pagination）、范围筛选（range selection）、条件过滤（filtering）和/或截断（truncation）**，并配上合理的默认参数。在 Claude Code 中，我们默认将单次工具返回限制在 25,000 tokens 以内。尽管我们预计智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求依然不会消失。

 如果你选择截断返回结果，**务必在截断提示中给出有帮助的引导指令**。你可以直接鼓励智能体采取更省 Token 的策略，例如在知识检索任务中发起多次小而精准的搜索，而不是一次宽泛的大搜索。同样，当工具调用报错（例如参数校验失败）时，不要只抛出一串晦涩的错误码或报错堆栈，而要对错误响应做提示词工程优化——**清晰传达具体且可执行的改进方式**。

> **【图表说明】** 官方原图：截断后的工具响应示例（Stripe 交易搜索）——展示前 3 条与总量摘要，并明确引导智能体按供应商、金额区间筛选或翻页。



> **【图表说明】** 官方原图（反例）：无益的错误响应示例——仅返回原始 422 JSON 报错，缺乏修复指引。



> **【图表说明】** 官方原图（正例）：有帮助的错误响应示例——说明失败原因，给出合法 `userId` 示例，并提示可调用 `user_search()` 获取 ID。

   **官方图注：**工具截断与错误响应可以引导智能体采取更省 Token 的工具使用行为（如使用筛选器或分页），或直接提供格式正确的工具输入示例。

### 原则 5：对工具描述做提示词工程优化（Prompt-engineering your tool descriptions）

 最后，也是提升工具表现最有效的方法之一：**对工具描述与规格说明做提示词工程优化**。因为这些文本会被直接加载进智能体的上下文，它们共同引导着智能体的工具调用行为。

 撰写工具描述与规格时，试想你会如何向团队里的新同事介绍这个工具：把你大脑里习以为常的隐含背景——专用查询语法、垂直领域术语定义、底层资源之间的关联关系——全部显式写出来。通过清晰的描述（并配合严格的数据模型校验）消除歧义。尤其要注意参数命名绝不含糊：**与其把参数叫做 `user`，不如明确命名为 `user_id`。**

 配合你的评估体系，你可以更有把握地衡量每次提示词工程微调带来的增益。哪怕是对工具描述做极细微的打磨，也能带来戏剧性的提升——在我们对工具描述进行精准优化后，Claude Sonnet 3.5 在 [SWE-bench Verified](https://www.anthropic.com/engineering/swe-bench-sonnet) 评估中取得了业界领先的表现，错误率大幅下降、任务完成率显著攀升。

 你可以在我们的 [开发者指南（Developer Guide）](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#best-practices-for-tool-definitions) 中找到更多工具定义的最佳实践。如果你正在为 Claude 构建工具，我们还建议了解工具是如何被动态加载到 Claude [系统提示词（system prompt）](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#tool-use-system-prompt) 中的。最后，如果你在为 MCP 服务器编写工具，利用 [工具注解（tool annotations）](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) 可以明确披露哪些工具需要访问开放外部环境或执行破坏性变更。

## 四、展望（Looking ahead）

 要为智能体打造真正高效的工具，我们需要将软件开发范式从可预测的确定性模式，转向面向非确定性系统的设计思维。通过本文介绍的评估驱动迭代流程，我们归纳出好工具的共性：**意图明确、边界清晰、惜 Token 如金、易于在多样化工作流中组合，并能让智能体凭直觉顺畅解决现实任务。**

 未来，无论是 MCP 协议演进还是底层大语言模型升级，智能体与世界交互的具体机制必将持续变化。但只要坚持这套系统化、评估驱动的优化方法，就能确保你的工具随着智能体能力的进化而同步成长。

- **把后端 5 个零散接口合并成 1 个业务高信号 MCP 工具**：不要把 ERP/CRM 的原始 CRUD 直接透传给 GPT-6.2，而是封装成 `crm_get_customer_context(customer_id, response_format)`，一次返回近 90 天订单、售后记录与会员等级，并默认走 `concise` 省下 65% Token。
- **按业务域做好命名空间与风险注解**：给客服/运营 MCP 统一前缀（如 `oms_order_search`、`crm_ticket_reply`、`promo_coupon_issue`），并在 MCP 工具注解中明确标出只读查询 vs. 发券/退款等破坏性写操作，便于网关强制拦截或触发二次确认。
- **把报错信息写成“纠偏提示词”**：当模型传错参数（例如订单号格式不符或退款额超限）时，不要只抛 `HTTP 400`，而是返回可读指引（如“订单号需以 ORD- 开头，示例：ORD-20261124-001；可先调用 oms_order_search 按手机号查号”），大幅降低无意义重试。
- **用 Codex 跑真实工单轨迹自动打磨工具**：挑出 20 条需要连调 3–8 次工具的复杂客诉与异常订单巡检，跑完后把完整工具调用日志喂给 Codex，让它直接帮你找出冗余调用、重构参数描述并用留出工单集验证。
