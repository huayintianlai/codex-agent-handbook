Building effective agents

> **官方注记（Note）**


自 2024 年 12 月本文发布以来，文中提及的许多工具生态已经发生了变化。关于我们当前的最新实践，请参阅 [《我们如何构建 Claude Managed Agents》](https://www.anthropic.com/engineering/managed-agents)（可对应参考本辑第 06 篇）及 [Managed Agents 官方文档](https://platform.claude.com/docs/en/managed-agents/overview)。

 过去一年里，我们与来自各行各业的数十个团队合作，共同构建大语言模型（LLM）智能体。我们发现了一个非常一致的规律：**最成功的落地实现，往往并没有依赖复杂的框架或专用库，而是基于简单、可组合的模式构建而成的。**

 在本文中，我们将分享与客户合作以及我们自身构建智能体所积累的经验，并为开发者提供构建高效智能体的实用建议。

## 一、什么是智能体？（What are agents?）

 “智能体（Agent）”可以有多种定义方式。有些客户将其定义为能够长时间独立运行、借助各类工具完成复杂任务的全自主系统；另一些客户则用这个词来形容严格按预定义流程写死的强约束实现。在 Anthropic，我们将所有这些变体统称为**智能体系统（agentic systems）**，但在架构上对**工作流（workflows）**和**智能体（agents）**做出了重要区分：

- **工作流（Workflows）**：通过**预定义的代码路径**来编排大语言模型与工具的系统。
- **智能体（Agents）**：由大语言模型**动态自主指挥自身流程与工具调用**、并掌控任务完成方式的系统。


 下文将详细探讨这两类智能体系统。在附录 1（“实践中的智能体”）中，我们还将介绍客户在两个具体领域中应用这类系统所获得的显著价值。

## 二、何时使用（以及何时不使用）智能体（When and when not to use agents）

 使用 LLM 构建应用时，我们建议**先寻找尽可能最简单的解决方案**，仅在确实需要时才增加复杂度。这有时意味着根本不需要构建智能体系统。智能体系统通常是以更高的延迟和成本来换取更好的任务表现，你必须审慎权衡这种取舍是否值得。

 当确实需要更高的复杂度时：对于定义清晰的任务，**工作流**能提供可预测性与一致性；而当大规模场景需要灵活性和模型驱动的自主决策时，**智能体**是更好的选择。不过，对于绝大多数应用而言，通过检索增强（retrieval）和上下文示例（in-context examples）优化单次 LLM 调用，通常就已经足够了。

## 三、何时以及如何使用框架（When and how to use frameworks）

 市面上有不少可以简化智能体系统实现的框架，包括：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
- AWS 推出的 [Strands Agents SDK](https://strandsagents.com/latest/)；
- [Rivet](https://rivet.ironcladapp.com/)，一款拖拽式图形界面的 LLM 工作流构建工具；以及
- [Vellum](https://www.vellum.ai/)，另一款用于构建和测试复杂工作流的图形界面工具。


 这些框架通过封装标准的底层任务（如调用 LLM、定义与解析工具、串联调用链）降低了上手门槛。但它们往往也会引入额外的抽象层，掩盖底层的提示词与模型响应，让排障变得困难；更常见的是，即便更简单的方案本就够用，框架也容易诱使开发者平添不必要的复杂度。

 我们建议开发者**直接从调用 LLM API 起步**：许多核心模式只需几行代码即可实现。如果你确实决定使用某个框架，请务必摸清其底层代码实现——对框架底层机制的错误假设，是客户最常见的报错根源之一。

 如需查看部分示例实现，请参阅我们的 [Cookbook 示例代码库](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 四、基础组件、工作流与智能体（Building blocks, workflows, and agents）

 本节将探讨我们在生产环境中最常看到的智能体系统模式。我们将从最基础的构建模块——增强型 LLM（the augmented LLM）出发，逐步提升复杂度，从简单的组合式工作流过渡到自主智能体。

### 基础模块：增强型 LLM（The augmented LLM）

 智能体系统的基本构建模块，是经过**检索（retrieval）、工具（tools）和记忆（memory）**等能力增强的大语言模型。如今的模型已经能够主动运用这些能力——自己生成搜索查询、选择合适的工具，并决定保留哪些信息。

> **【图表说明】** 官方原图（中文化）：增强型 LLM（The augmented LLM）——集成检索、工具与记忆能力的核心构建模块。



 在实现这一模块时，我们建议重点关注两个方面：根据你的具体业务场景量身定制这些能力，并确保为 LLM 提供清晰、文档完备的接口。实现这些增强能力的方式有很多，其中一种便是通过我们发布的**[模型上下文协议（Model Context Protocol，简称 MCP）](https://www.anthropic.com/news/model-context-protocol)**，它让开发者只需完成一个简单的[客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)，即可接入不断壮大的第三方工具生态。

 在本文剩余部分，我们默认每一次 LLM 调用都具备上述增强能力。

### 工作流模式 1：提示词链（Prompt chaining）

 提示词链将一个任务拆解为一系列有序步骤，每次 LLM 调用处理上一步的输出。你可以在任意中间步骤加入程序化检查（见下图中的“门控 / gate”），确保整个流程始终在正轨上运行。

> **【图表说明】** 官方原图（中文化）：提示词链工作流（The prompt chaining workflow）——分步拆解并配合门控校验。



**适用场景：**当任务能够干净、清晰地拆解为固定子任务时，这种工作流最为理想。其核心目标是通过让每次 LLM 调用处理更简单的子任务，用一定的延迟换取更高的准确率。

**典型示例：**

- 先生成营销文案，再将其翻译为另一种语言；
- 先撰写文档大纲，程序检查大纲是否满足特定标准，然后再基于该大纲撰写正文。


### 工作流模式 2：路由分流（Routing）

 路由模式先对输入进行分类，再将其定向到专门的后续处理任务。这种模式实现了关注点分离，允许为不同类别编写更具针对性的提示词——如果不做路由分流，针对某一类输入调优提示词，往往会拖累其他类型输入的表现。

> **【图表说明】** 官方原图（中文化）：路由分流工作流（The routing workflow）——先分类再定向至专门处理器。



**适用场景：**适用于包含若干界限清晰的类别、适合分开处理的复杂任务，且分类本身可以通过 LLM 或传统分类模型/算法准确完成。

**典型示例：**

- 将不同类型的客户服务咨询（常规问题、退款请求、技术支持）分流到各自专属的下游流程、提示词和工具中；
- 将简单常见的问题路由给更小、更具性价比的模型（如 Claude Haiku 4.5），将复杂罕见的问题路由给能力更强的模型（如 Claude Sonnet 4.5），以实现最优的性价比与效果平衡。


### 工作流模式 3：并行化（Parallelization）

 有时可以让多个 LLM 同时处理同一任务，再通过程序聚合它们的输出。并行化工作流主要表现为两种核心形态：

- **切片并行（Sectioning）**：将任务拆分为多个相互独立的子任务并同时运行。
- **投票并行（Voting）**：将同一个任务运行多次，以获得多样化的输出并做综合决策。


> **【图表说明】** 官方原图（中文化）：并行化工作流（The parallelization workflow）——切片并发或多次投票后由聚合器汇总。



**适用场景：**当拆出的子任务可以并行加速，或者需要多个视角/多次尝试来提高结果置信度时，并行化非常有效。对于包含多维度考量的复杂任务，如果将每个维度交给独立的 LLM 调用分别处理，让每个模型实例只专注把关单一维度，表现通常会好得多。

**典型示例：**

- **切片并行（Sectioning）**：

- 实现安全护栏（guardrails），让一个模型实例处理用户请求，同时让另一个实例专门筛查不当内容或违规请求——这通常比让同一次 LLM 调用兼顾核心回复和内容审查表现更好；
- 自动化评估（evals）以评测 LLM 性能，让每次 LLM 调用分别评估模型在给定提示词上某一特定维度的表现。

- **投票并行（Voting）**：

- 审查代码安全漏洞，用多组不同提示词并行审查代码，只要发现隐患即标记；
- 评估某段内容是否不当，用多个提示词从不同维度评估，或通过设置不同的投票阈值来权衡误报与漏报。



### 工作流模式 4：编排者—执行者（Orchestrator-workers）

 在编排者—执行者工作流中，一个中枢 LLM 动态拆解任务，将子任务委派给多个执行者（worker）LLM，并最终汇总它们的结果。

> **【图表说明】** 官方原图（中文化）：编排者—执行者工作流（The orchestrator-workers workflow）——中枢动态拆解并汇总子任务。



**适用场景：**非常适用于**事前无法预测需要哪些子任务**的复杂场景（例如在编程任务中，需要修改多少个文件、每个文件具体怎么改，完全取决于当前输入）。虽然在拓扑结构上与“并行化”相似，但二者最核心的区别在于灵活性——子任务不是预先写死的，而是由编排者根据具体输入实时决定的。

**典型示例：**

- 每次任务都需要对多个文件进行复杂改动的 AI 编程产品；
- 需要从多个信息源搜集并分析潜在相关信息的深度检索任务。


### 工作流模式 5：评估者—优化者（Evaluator-optimizer）

 在评估者—优化者工作流中，一个 LLM 调用负责生成输出，另一个 LLM 调用负责在循环中提供评估与修改反馈。

> **【图表说明】** 官方原图（中文化）：评估者—优化者工作流（The evaluator-optimizer workflow）——生成与评审迭代闭环。



**适用场景：**当我们拥有明确的评估标准，且迭代打磨能够带来可衡量的质量提升时，这种模式尤为有效。判断其是否适用的两个重要信号是：第一，当人类给出明确修改意见时，LLM 的输出确实能肉眼可见地变好；第二，LLM 本身也有能力稳定给出这类反馈。这类似于人类作家反复修改、打磨稿件的写作过程。

**典型示例：**

- 文学翻译：译者 LLM 初稿可能遗漏细微语感，而评估者 LLM 可以指出不足并提出润色建议；
- 需要多轮搜索与分析才能汇集完整信息的复杂搜索任务，由评估者决定是否需要继续深挖检索。


### 自主智能体（Agents）

 随着大语言模型在理解复杂输入、推理与规划、可靠调用工具以及从错误中恢复等关键能力上日趋成熟，自主智能体正逐步走向生产环境。智能体通常以人类用户的指令或交互式讨论为起点；一旦任务明确，智能体便会自主规划并独立运行，必要时再回到人类这里请求补充信息或判断。在执行过程中，至关重要的环节是让智能体在每一步都能从环境中获取**“客观真值（ground truth）”**（例如工具调用的返回结果或代码执行输出），以此评估自身进展。智能体可以在关键检查点或遇到阻塞时暂停，等待人类反馈。任务通常在完成后结束，但实践中也常常设定停止条件（例如最大迭代步数）以保持系统可控。

 智能体虽然能够处理极其复杂的任务，但其底层实现往往出奇地直白：**本质上就是 LLM 在一个循环中，根据环境反馈持续调用工具。**因此，清晰、周密地设计工具集及其文档显得尤为关键。我们在附录 2（“为你的工具做提示词工程”）中详细展开了工具开发的最佳实践。

> **【图表说明】** 官方原图（中文化）：自主智能体（Autonomous agent）——LLM 在环境行动与真实反馈闭环中持续自主决策。



**适用场景：**智能体适合解决开放式问题——这类问题很难甚至不可能提前预测所需的步骤数，也无法将路径写死在代码里。LLM 可能会连续运行很多轮，你必须对其决策能力有一定程度的信任。智能体的自主性使其非常适合在受信任的环境中规模化处理任务。

 同时，自主性也意味着更高的运行成本，以及错误层层叠加放大的潜在风险。我们强烈建议在**沙箱环境**中进行充分测试，并配备恰当的安全护栏（guardrails）。

**典型示例（来自我们自身的实践）：**

- 用于解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet)的编程智能体，需要根据任务描述修改多个代码文件；
- 我们的[“Computer Use”参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，让 Claude 直接操作计算机来完成任务。


> **【图表说明】** 官方原图（中文化）：编程智能体的顶层执行流程（High-level flow of a coding agent）。



## 五、组合与定制这些模式（Combining and customizing these patterns）

 上述基础模块并非僵硬的教条，而是开发者可以根据不同业务场景灵活裁剪与组合的常见模式。与所有 LLM 功能一样，成功的关键在于**持续度量表现并迭代优化实现**。需要再次强调：**只有在能够明确证明效果提升的前提下，才应该增加系统复杂度。**

## 六、总结（Summary）

 在 LLM 领域取得成功，靠的不是构建最复杂炫酷的系统，而是构建**最契合你需求**的系统。从简单的提示词起步，借助全面的评估（evaluation）不断优化，仅在更简单的方案力不从心时，才引入多步骤的智能体系统。

在实现智能体时，我们坚持以下三条核心原则：

1. **保持设计的简洁性（Maintain simplicity）**；
1. **优先保证透明度（Prioritize transparency）**，显式展示智能体的规划步骤；
1. **精心打磨智能体-计算机界面（ACI）**，做好详尽的工具文档编写与测试。


 框架可以帮助你快速起步，但在迈向生产环境时，别犹豫，果断削减多余抽象层、回归基础组件来构建。遵循这些原则，你将能够打造出不仅强大，而且可靠、易维护、真正值得用户信赖的智能体。

## 七、附录 1：实践中的智能体（Appendix 1: Agents in practice）

 通过与客户合作，我们发现了两个极具前景的 AI 智能体落地场景，它们充分展现了上述模式的实用价值。这两个场景共同体现了智能体最具优势的任务特征：同时需要对话与行动、拥有清晰的成功标准、支持反馈闭环，并能融入有意义的人类监督。

### A. 客户支持（Customer support）

 客户支持将人们熟悉的聊天机器人交互，与通过工具集成获得的强大执行能力结合在一起。它天然契合更开放式的智能体形态，原因在于：

- 客服交互天然遵循对话流程，同时又需要访问外部信息并执行具体动作；
- 可以通过工具拉取客户资料、历史订单和知识库文档；
- 退款发放、工单更新等操作可以通过程序化方式安全执行；以及
- 成功与否可以通过用户确认的问题解决率清晰衡量。


 多家企业已经通过“仅按成功解决的问题计费”的按量付费商业模式，验证了这一路径的可行性，也充分体现了对智能体效果的信心。

### B. 编程智能体（Coding agents）

 软件开发领域已展现出 LLM 能力的巨大潜力，相关功能正从代码补全演进为自主解决问题。智能体在编程领域尤为高效，原因在于：

- 代码方案可以通过自动化测试进行客观验证；
- 智能体能够利用测试报错作为反馈持续迭代修复；
- 问题空间定义清晰且高度结构化；以及
- 输出质量可以客观度量。


 在我们自己的实现中，智能体如今仅凭 Pull Request 描述即可解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准测试中的真实 GitHub Issue。不过，尽管自动化测试有助于验证功能正确性，但人工代码审查对于确保方案契合更宏观的系统需求依然至关重要。

## 八、附录 2：为你的工具做提示词工程（Prompt engineering your tools）

 无论构建哪一种智能体系统，工具（tools）大概率都是核心组成部分。开发者在 API 中定义[工具](https://www.anthropic.com/news/tool-use-ga)的精确结构与调用规范，Claude 就能借此与外部服务和 API 交互。当 Claude 决定调用某个工具时，会在 API 响应中返回一个 [`tool use` 块](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。**工具的定义与规格说明，应当获得与主提示词同等程度的提示词工程投入。**在本附录中，我们简要介绍如何对工具进行提示词工程优化。

 同一个操作往往有多种表达格式。例如，指定文件修改既可以用 `diff` 格式，也可以重写整个文件；输出结构化代码时，既可以放在 Markdown 中，也可以放进 JSON 字段里。在传统软件工程中，这类格式差异只是表面形式，彼此可以无损转换。但对大语言模型来说，某些格式的书写难度要远远高于其他格式：写 `diff` 要求模型在真正写出新代码之前，就提前准确算出代码块头部（chunk header）里变动了多少行；而在 JSON 里写代码（相比 Markdown），则需要对换行符和引号做大量额外转义。

我们在选择工具格式时遵循以下建议：

- 给模型留出足够的 Token 去“思考”，避免它在还没想清楚前就把自己写进死胡同；
- 尽量选用贴近互联网文本中自然常见形态的格式；
- 消除不必要的格式“心智负担”（overhead），例如要求模型精确统计成千上万行代码的行数，或手动对所写代码做字符串转义。


 一条非常实用的经验法则是：**想想你在人机界面（HCI）上投入了多少心血，就应当计划投入同等的心血去打造优秀的智能体-计算机界面（ACI）。**具体做法包括：

- **站在模型的角度换位思考**：仅看工具描述和参数，用法是否一目了然，还是需要费劲琢磨？如果连你都要仔细想半天，模型大概率也一样。一份好的工具定义通常包含调用示例、边界情况说明、输入格式要求，以及与其他相似工具的明确界线。
- **优化参数命名与描述**：怎样调整参数名和说明才能让含义更直白？把这当作在给团队里刚入职的初级工程师写一份极佳的函数文档（docstring）。当系统里存在大量相似工具时，这一点尤为重要。
- **实测模型如何使用你的工具**：在我们的 [Workbench](https://console.anthropic.com/workbench) 测试台中跑大量真实输入样本，观察模型究竟在哪里犯错，然后持续迭代。
- **给工具做[防呆设计（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)**：通过改进参数设计，从源头上让模型更难犯错。


 在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建编程智能体时，**我们花在优化工具上的时间，实际上比优化整体提示词还要多。**举个例子：我们发现一旦智能体离开项目根目录，使用相对文件路径的工具就频频出错。为了彻底根治这个问题，我们直接把工具改为**始终要求传入绝对文件路径**——结果模型从此使用得完美无缺。
